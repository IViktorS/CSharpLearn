# 1.15 Рекурсия (базовый случай, стек вызовов, StackOverflow)

Тема идёт в ускоренном режиме: механизм стека вызовов уже разобран в 1.3, здесь он только применяется. Задачи — `Recursion.cs`, запуск `dotnet run --project Basics -- 1.15`.

## 1. Зачем / какую проблему решает

Есть данные, устроенные **самоподобно**: у папки внутри папки, у узла дерева — узлы, у выражения `(2 + (3 * 4))` — выражения. Обойти их циклом нельзя: заранее неизвестно, сколько будет уровней вложенности, и на каждом уровне надо делать то же самое.

Рекурсия — это когда метод в своей работе вызывает сам себя для **той же задачи меньшего размера**. Обход папки сводится к обходу её подпапок, сумма дерева — к сумме поддеревьев.

Альтернатива существует: любую рекурсию можно переписать циклом, но тогда стек, который рекурсия получала бесплатно, придётся вести руками — `Stack<T>` и явные push/pop. Иногда это и нужно (см. «Когда что»), но код становится длиннее.

## 2. Как устроено: это ровно стек вызовов из 1.3

Никакого отдельного механизма у рекурсии нет. Работает то же, что и при любом вызове метода:

- каждый вызов создаёт **кадр стека** — аргументы, локальные переменные, адрес возврата;
- кадр живёт, пока вызов не вернулся;
- вернулся — кадр снимается.

Рекурсия отличается только тем, что одновременно живёт **много кадров одного и того же метода**. Вызов `Sum(node)` на глубине 5 означает пять кадров `Sum` в стеке, каждый со своей копией локальных переменных.

Отсюда сразу два следствия, и оба важны:

**Глубина ограничена.** Стек потока — фиксированный блок памяти (по умолчанию порядка 1 МБ). Кончился — процесс умирает. Это не «много памяти», а именно фиксированный лимит, в отличие от кучи.

**Предел зависит от размера кадра, а не только от метода.** Чем больше локальных переменных, тем толще кадр и тем меньше вызовов поместится. Замерено на одной машине:

| Рекурсивный метод | Досчитал до глубины |
|---|---|
| без локальных переменных | ~12 000–14 000 |
| с локальной `struct` на 128 байт | ~6 000–8 000 |

Один и тот же лимит стека, разница только в толщине кадра — и вдвое меньшая допустимая глубина.

## 3. Как пишется

Два обязательных элемента, и оба обязательны именно вместе:

1. **Базовый случай** — условие, при котором метод возвращает результат, не вызывая себя.
2. **Шаг, приближающий к базовому случаю** — каждый следующий вызов получает задачу *меньше* предыдущей.

```csharp
static int Factorial(int n)
{
    if (n <= 1) return 1;        // базовый случай
    return n * Factorial(n - 1); // шаг: n уменьшается
}
```

Проверять надо оба. Базовый случай, к которому шаг не приближает, бесполезен:

```csharp
static int Broken(int n)
{
    if (n == 0) return 0;         // базовый случай есть...
    return Broken(n + 1);         // ...но шаг уходит ОТ него
}
```

## 4. Грабли

**1. `StackOverflowException` нельзя поймать.** Это главная неожиданность темы. `try/catch` вокруг рекурсии не спасает — процесс убивается немедленно, обработчик не выполняется, `finally` не выполняется.

Проверено: `catch (Exception)` вокруг бесконечной рекурсии не сработал, в консоль ушло `Stack overflow.` со стектрейсом и процесс завершился.

Причина понятна из механизма: чтобы выполнить обработчик, нужен кадр стека, а стек уже кончился. Начиная с .NET 2.0 это состояние считается невосстановимым, и среда не пытается его чинить.

Практический вывод: **глубину надо ограничивать самому** — параметром `depth` или счётчиком, — потому что «подстраховаться `catch`'ем» физически невозможно. Это единственное исключение из привычного «упало — поймаем и обработаем».

**2. C# не гарантирует оптимизацию хвостовых вызовов.** Даже если рекурсивный вызов стоит последней операцией (хвостовая рекурсия), компилятор C# не превращает его в цикл — кадры реально накапливаются. Полагаться на такую оптимизацию нельзя; в языках вроде F# ситуация другая.

**3. Повторные вычисления.** Наивный Фибоначчи вызывает себя дважды на каждом уровне, и число вызовов растёт экспоненциально: одни и те же значения считаются заново тысячи раз. Рекурсия удобно записывается, но легко скрывает такую катастрофу.

**4. Глубина, зависящая от входных данных, — дыра в надёжности.** Рекурсия по списку из 100 элементов работает; по списку из 100 000, пришедшему извне, уронит процесс. Если глубину задаёт не разработчик, а данные — рекурсия небезопасна.

**5. Циклическая ссылка в «дереве».** Если структура на самом деле граф и содержит цикл, базовый случай недостижим, сколько бы он ни был правильно написан. Лечится множеством посещённых узлов.

**6. Взаимная рекурсия.** `A` вызывает `B`, `B` вызывает `A`. Базовый случай существует в паре, а не в одном методе, и потерять его гораздо легче.

## 5. Когда что

| Ситуация | Что писать |
|---|---|
| Дерево, граф, вложенные папки, разбор выражения | рекурсия |
| Линейный проход по коллекции | цикл |
| Глубина определяется внешними данными | цикл + свой `Stack<T>` |
| Одни подзадачи повторяются (Фибоначчи, пути в сетке) | рекурсия + кеш результатов |

Про третью строку стоит сказать отдельно, потому что это прямое следствие 1.3: **свой `Stack<T>` живёт в куче**, а стек вызовов — фиксированный блок памяти потока. Переписав рекурсию на явный стек, вы меняете жёсткий лимит на растущую структуру и перестаёте зависеть от глубины данных.

## 6. Опирается на

Назвал пользователь:

- **1.1 Value types vs reference types** — каждый вызов получает свои копии параметров и локальных переменных. `maxDepth` в кадре одного узла и `maxDepth` в кадре другого — разные переменные с одинаковым именем.
- **1.5 `null`** — проверка `node == null` и различение «пустой список» против «ссылки нет».
- **1.6 Свойства** (тонкая связь) — `List.Count` это свойство; на механику темы не влияет.

Дополнено при проверке:

- **1.3 Stack vs Heap — несущая тема.** Вся 1.15 есть 1.3 в действии: кадр на каждый вызов, кадр живёт до возврата, стек — фиксированный блок памяти потока. Отсюда и предел глубины, и то, почему спуск в ветку не портит расчёт в вызывающем кадре.
- **1.10 `static`** — счётчики `calls` и `depth` работают именно потому, что принадлежат **типу**, а не кадру, и переживают все вызовы. Локальная переменная на их месте считать бы не смогла. Прямой контраст «своё на каждый кадр» против «одно на тип».
- **1.2 `struct` vs `class`** — `DownFat` исчерпывает стек вдвое быстрее, потому что структура лежит **внутри кадра целиком** (значимый тип). Будь `Fat` классом, в кадре осталась бы только ссылка и глубина почти не изменилась бы.

### Замечание из решения

Формулировка пользователя, к которой он пришёл сам и которая и есть суть темы: «мы же ещё в методе находимся, где это максимальное значение сохранено и никуда не делось, а мы просто провалились в новую ветку и считаем пока в ней отдельно». Состояние хранит стек вызовов — сохранять его вручную не нужно.

### Про базовый случай у коллекции

Явная проверка `if (node.Children.Count == 0)` в обоих методах **избыточна**: `foreach` по пустому списку не делает ничего, и базовый случай получается сам. Для узла со ссылками `Left`/`Right` это было бы не так — там пришлось бы проверять `null`.
