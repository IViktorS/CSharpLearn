# 1.3 — Stack vs Heap

## Две области памяти
- **Stack (стек)** — у каждого потока свой. Хранит **кадры вызовов** (локальные переменные, параметры, адрес возврата). LIFO. Освобождение **мгновенное и детерминированное** — при выходе из метода, простым сдвигом указателя. Маленький (~1 МБ) → бесконечная рекурсия = `StackOverflowException`.
- **Heap (куча)** — одна на приложение. Хранит **объекты ссылочных типов**. Освобождает **GC**, недетерминированно, с паузами.

## Главный миф
«`struct` всегда в стеке» — **неверно**. Где лежат данные значимого типа, зависит от **места объявления**, а не от того, что это `struct`:
- локальная `struct` в методе → в стеке;
- поле-`struct` внутри `class` → в куче (inline внутри объекта-владельца);
- `struct` в массиве/`List` → в куче;
- boxing → в куче.

## Ссылочный тип
`var p = new Person();`: сам объект `Person` → в **куче**; переменная `p` (ссылка ~8 байт) → в **стеке**, указывает на объект.

## Зачем различать
1. **GC**: всё в куче собирает GC. Много мелких объектов → частые сборки → паузы.
2. **Время жизни**: данные в стеке умирают при выходе из метода → нельзя вернуть `ref` на локальную переменную (кадр снят, память недействительна, CS8168).

## Эксперимент (задача)
5 млн `class`-объектов → **12 сборок Gen0**; массив из 5 млн структур → **0 сборок** (один объект-массив).
Вывод: **меньше объектов в куче → меньше работы GC** (не «переместили в стек»).

## Оговорка
Стек/куча — деталь реализации CLR, а не спецификации C#. Но как ментальная модель для junior/middle — рабочая.
