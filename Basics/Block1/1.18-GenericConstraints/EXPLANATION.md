# 1.18 Ограничения дженериков (`where T : ...`)

Продолжение 1.17. Там тема кончилась четырьмя запретами — здесь они снимаются.

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; **[измерено]** — есть числа замера; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

> Мини-справка: **интерфейс** — список членов, которые тип обязуется иметь. Здесь он нужен только как чёрный ящик: «`IComparable<T>` означает, что у типа есть метод `CompareTo`». Подробно — тема 2.2.

## 1. Зачем / какую проблему решает

В 1.17 про `T` внутри не было известно ничего, и компилятор отказывал четырьмя ошибками: `new T()`, `T x = null`, `a < b`, `a.Length`. Отказывал честно — он обязан собрать тело один раз, годное для любого будущего аргумента.

Ограничение — способ сузить «любой будущий аргумент» до «любой, который умеет вот это». Это **договор**: ты обещаешь компилятору, что подставишь только подходящий тип, он в обмен разрешает пользоваться обещанным.

Формула темы: **ограничение покупает возможности внутри ценой свободы снаружи.** Каждое `where` что-то разрешает в теле и одновременно выкидывает часть типов из допустимых. Бесплатных ограничений не бывает, и вопрос всегда в том, какую именно свободу ты отдаёшь.

> [док] [Constraints on type parameters](https://learn.microsoft.com/dotnet/csharp/programming-guide/generics/constraints-on-type-parameters)

## 2. Как устроено

**Ограничение — не проверка в рантайме.** Всё решается на этапе компиляции, в двух местах:

- **в точке вызова** проверяется аргумент типа — не подошёл, ошибка сборки (CS0452 / CS0453);
- **внутри тела** разрешаются операции, которые обещаны ограничением.

Ни `is`, ни приведения, ни коробки в готовом коде не появляется. Это прямое продолжение того, что было в 1.17: тип — параметр компиляции, а не значение.

### Виды ограничений

| Ограничение | Что обещает про `T` | Что можно писать в теле |
|---|---|---|
| `where T : struct` | значимый тип, **кроме `Nullable`**: `T` не может быть `int?` | `default(T)` — нули |
| `where T : class` | ссылочный тип | `T x = null` |
| `where T : notnull` | значимый или ссылочный, но не `null` | снимает предупреждения NRT |
| `where T : Базовый` | наследник класса | члены этого класса |
| `where T : IИнтерфейс` | реализует интерфейс | члены интерфейса |
| `where T : new()` | есть конструктор без параметров | `new T()` |
| `where T : U` | наследник другого параметра типа | члены `U` |
| `where T : Enum` | перечисление | члены `System.Enum`; см. ниже про `struct, Enum` |
| `where T : Delegate` | делегат | члены `System.Delegate` (Блок 3) |
| `where T : unmanaged` | значимый тип без ссылок внутри | работа с указателями, `sizeof` |

Последние три появились в C# 7.3; до этого компилятор их запрещал, и в старом коде вместо `where T : Enum` встречается `where T : struct` с проверкой типа уже в рантайме.

> **Про колонки.** Вторая колонка — про то, **каким может быть сам `T`** в точке вызова. Третья — про то, **что становится законно написать в теле**. Это разные вопросы, и путать их легко: запись `T?` относится к первой колонке не больше, чем ко второй, — она не разрешение, а обозначение другого типа, построенного из `T`. Разобрана отдельно ниже.

Несколько ограничений на один параметр пишутся через запятую, несколько параметров — своим `where` на каждый:

```csharp
static TResult Convert<TSource, TResult>(TSource source)
    where TSource : class, IComparable<TSource>
    where TResult : struct
```

**Порядок внутри одного `where` жёсткий:** сначала первичное (`class` / `struct` / базовый класс), потом интерфейсы, `new()` — всегда последним. Нарушение — ошибка сборки.

**[проверено]:**
```csharp
static T Make<T>() where T : new(), Animal => new T();
// error CS0401: ограничение new() должно быть последним
```

## 3. Что именно снимает каждое ограничение

### `where T : struct` и `where T : class` — и главный сюрприз темы

**[проверено]**, `default(T)` под ограничениями:

```
where T : struct, T = int      -> [0]
where T : struct, T = DateTime -> [01.01.0001 0:00:00]
where T : class,  T = string   -> [null]
```

**Чем `T` быть не может.** `Nullable<int>` формально **является** значимым типом (`typeof(int?).IsValueType == true` **[проверено]**), но под `where T : struct` он не проходит — это отдельный запрет:

```
H.Take<int?>(x)
error CS0453: тип "int?" должен быть типом значения,
              НЕ ДОПУСКАЮЩИМ значения Null            [проверено]
```

В рантайме флаг так и называется — `NotNullableValueTypeConstraint`. Причина запрета: иначе `T?` внутри означало бы `int??`, вложенный `Nullable`, которого в языке нет.

Разграничение, которое стоит держать твёрдо:

| | Можно ли |
|---|---|
| `T` = `int?` | **нет**, CS0453 |
| `T?` = `int?` при `T` = `int` | **да**, это и есть `Nullable<int>` |

То есть `T?` в сигнатуре — **не разрешение подставить `int?` вместо `T`**, а другой тип, построенный из `T`. Сам `T` при этом остаётся `int`. **[проверено]**: метод `TakeMaybe<T>(T? maybe) where T : struct` принимает `int?` со значением и без, `HasValue` внутри доступен.

А вот то, ради чего эти два ограничения стоит запомнить вместе. **Запись `T?` означает разные вещи в зависимости от того, какое ограничение стоит рядом.**

```csharp
static T? MaybeStruct<T>(bool give) where T : struct => give ? default(T) : null;
static T? MaybeClass<T>(bool give)  where T : class  => give ? default! : null;
```

**[проверено]**, статические типы результата:

```
MaybeStruct<int>    -> System.Nullable`1[System.Int32]   HasValue доступен: True
MaybeClass<string>  -> System.String                     (только аннотация NRT)
```

Один и тот же символ `?` — в первом случае **настоящая обёртка** `Nullable<T>` с полями `HasValue`/`Value` (1.5), во втором **пометка для анализатора**, никакой обёртки в рантайме нет. Отсюда практический вывод, который висел незакрытым с задачи 3 темы 1.17: «значение может отсутствовать» — это **два разных решения**, и выбрать одно на оба случая нельзя. Либо два ограниченных типа, либо механизм, не опирающийся на `null` вовсе.

### `where T : Enum` — и почему на практике пишут `struct, Enum`

Ограничение по `Enum` встречается часто: оно позволяет написать типизированную обёртку над теми методами `System.Enum`, которые исторически работают с `object` и требуют приведений.

Но у него есть тонкость, из-за которой почти везде пишут не так, как кажется естественным.

`System.Enum` — это **абстрактный ссылочный тип**, общий базовый класс всех перечислений. Поэтому он **сам удовлетворяет** ограничению `where T : Enum`:

```csharp
static string Loose<T>(T v)  where T : Enum        => $"{v}";
static string Strict<T>(T v) where T : struct, Enum => $"{v}";

Enum asEnum = Status.Draft;

Loose<Enum>(asEnum)    // компилируется и работает  [проверено]
Strict<Enum>(asEnum)   // CS0453: тип "Enum" должен быть типом значения,
                       // не допускающим значения NULL              [проверено]
```

То есть `where T : Enum` в одиночку обещает «`T` — **какое-то** перечисление», а нужно обещание «`T` — **одно конкретное** перечисление». Разница видна на конкретном баге.

**Что ломается.** Метод написан, чтобы сравнить два значения одного перечисления:

```csharp
static bool SameCode<T>(T a, T b) where T : Enum
    => Convert.ToInt32(a) == Convert.ToInt32(b);
```

**[проверено]:**

```
SameCode<Enum>(Status.Draft, Color.Red) = True
```

Метод сообщил, что «черновик» и «красный» — одно и то же. Формально он прав, у обоих числовое значение 1. Но защитить от этого и должен был дженерик.

Строгую версию так вызвать нельзя: `T` пришлось бы сделать одновременно `Status` и `Color`.

```
error CS0411: аргументы типа не могут определяться по использованию   [проверено]
```

Именно `System.Enum` как ссылочный общий предок и есть та дверь, через которую в один вызов пролезают разные перечисления. `struct` её закрывает.

**Второе следствие — `default(T)`:**

```
Def<Enum>()         = null     [проверено]
DefStrict<Status>() = 0        [проверено]
```

Тело, написавшее внутри `default(T)`, при `T = Enum` получит `null`, а не нулевое значение перечисления, — и дальше `NullReferenceException`.

**Третье — упаковка, и она возникает не там, где кажется.** **[измерено]**, 1 000 000 вызовов, тело без приведений к `object`:

| Вариант | Байт на вызов |
|---|---|
| строгий, `T = Status` | **0** |
| нестрогий, `T = Enum`, значение уже упаковано | **0** |
| нестрогий, `T = Enum`, значение пришло как `Status` | **48** |

Упаковка происходит **в точке вызова**, когда конкретное значение перечисления приводится к `Enum`, а не внутри метода. Если у вызывающего уже лежит `Enum`, дополнительной цены нет. Поэтому довод про упаковку — третий по важности, а не первый.

**BCL поступает именно так** — проверено рефлексией по реальным сигнатурам:

```
Enum.GetValues<T>: NotNullableValueTypeConstraint + база Enum/ValueType
Enum.IsDefined<T>: NotNullableValueTypeConstraint + база Enum/ValueType
Enum.TryParse<T>:  NotNullableValueTypeConstraint (без базы Enum — старая сигнатура)
```

`NotNullableValueTypeConstraint` — это и есть `where T : struct`. То есть `Enum.GetValues<TEnum>()` объявлен как `where TEnum : struct, Enum`.

**Вывод для практики:** пишешь ограничение по перечислению — пиши `where T : struct, Enum`. Форма без `struct` не ошибочна, но оставляет открытой дверь, которую ты закрывал.

### `where T : new()`

```csharp
static T Create<T>() where T : new() => new T();
Create<Box>().V   // -> 0   [проверено]
```

Обещание — «у типа есть конструктор без параметров». У структур он есть всегда, у классов — только если объявлен или не объявлено ни одного.

### `where T : IИнтерфейс` — и где здесь деньги

Ограничение интерфейсом разрешает звать его члены. Но выгода не только в удобстве: **вызов через ограничение не создаёт коробку, а вызов через переменную интерфейсного типа создаёт.**

**[измерено]**, 2 000 000 вызовов `CompareTo` на `int`:

| Как вызвано | Выделено байт |
|---|---|
| `ViaConstraint<T>(T a, T b) where T : IComparable<T>` | **24** (всего, не на вызов) |
| `ViaInterface(IComparable<int> a, int b)` | **48 000 000** |

24 байта на два миллиона вызовов — это шум от прогрева, то есть **ноль**. Во второй строке — ровно 24 байта на каждый вызов: значение упаковывается при превращении в `IComparable<int>` (1.4). Причина в 1.17: для `T = int` JIT пишет отдельный машинный код под `int`, и обращаться к нему через коробку незачем.

Это главный практический ответ на вопрос «зачем вообще ограничения»: не только «компилятор разрешил `CompareTo`», но и «сделал это без аллокаций».

## 4. Грабли

**1. `int?` НЕ проходит `where T : struct`.**

```csharp
int? maybe = 5;
OnlyStruct(maybe);   // error CS0453: тип "int?" должен быть типом значения,
                     //               НЕ ДОПУСКАЮЩИМ значения null   [проверено]
```

`Nullable<int>` — сам по себе структура, и первая реакция «значит подходит» выглядит безупречно. Ограничение `struct` требует **не-nullable** значимый тип, иначе получился бы `Nullable<Nullable<int>>`.

**2. Ограничение не входит в сигнатуру метода.**

```csharp
public static void Save<T>(T item) where T : class { }
public static void Save<T>(T item) where T : struct { }
// error CS0111: тип уже определяет член "Save" с такими же типами параметров   [проверено]
```

Соблазн «напишу отдельную версию для ссылочных и для значимых» разбивается об это первым же. Компилятор различает методы по имени и типам параметров; `where` в этот список не входит. Лечится разными именами или разным числом параметров.

**3. `new()` — всегда последним** (CS0401, см. выше).

**4. Ограничение — обещание, а не проверка.** `where T : IComparable<T>` гарантирует наличие `CompareTo`, но ничего не говорит о том, что он написан правильно. Компилятор проверяет форму, не смысл.

**5. Ограничение сужает и то, чего ты не имел в виду.** `where T : class` выкидывает все структуры, включая `int`, `DateTime` и собственные value-типы. Часто оно ставится «чтобы можно было писать `null`», а платится возможностью применять код к числам.

**6. Чем больше `where`, тем уже применимость.** Обобщённый тип с четырьмя ограничениями подходит двум типам в программе — значит, обобщение не окупилось и проще написать конкретный код (грабля 7 из 1.17, с другой стороны).

## 5. Когда что

| Нужно внутри | Ограничение |
|---|---|
| сравнить два значения | `where T : IComparable<T>` |
| создать экземпляр | `where T : new()` |
| присвоить `null` как «значения нет» | `where T : class` — и понимать, что структуры отпали |
| обёртка «значение или его нет» на числах | `where T : struct`, работать с `T?` = `Nullable<T>` |
| вызвать метод своего базового класса | `where T : Базовый` |
| ничего конкретного, только хранить и отдавать | **ограничение не нужно** — см. 1.17 |

Правило: **ограничение ставится под операцию, которая уже понадобилась в теле.** Поставленное «на всякий случай» оно ничего не разрешает, зато сразу отрезает типы.

## 5б. Где встретится в реальном коде

- **`where T : class, new()` в фабриках и репозиториях** — самая частая пара. Признак: где-то внутри есть `new T()` и присвоение `null`.
- **`where T : IComparable<T>` в сортировках и структурах данных** — `SortedList`, самописные деревья, методы вида `Max<T>`. Если код собирается, но сортировка даёт бессмыслицу, смотреть надо на реализацию `CompareTo` у аргумента, а не на сам обобщённый код (грабля 4).
- **CS0111 на двух похожих методах** — почти всегда попытка сделать «версию для ссылочных и для значимых». Узнаётся мгновенно, лечится переименованием.
- **CS0453 на `int?`** — в коде, который «работал для `int`, а для `int?` перестал». Самая частая встреча ограничения `struct` в живой природе.
- **`where T : struct` вокруг `T?`** — признак, что автор целенаправленно делал «значение или его нет» для чисел. Рядом почти всегда есть парный тип или перегрузка для ссылочных: одним ограничением оба случая не берутся.
- **Замечание на ревью «зачем здесь `where`»** — проверяется за секунду: найди в теле операцию, которую это ограничение разрешает. Не нашлась — ограничение лишнее.

## 7. Будет позже

- **Интерфейсы целиком** (2.2) — здесь они были чёрным ящиком.
- **`IComparable<T>` и `IEquatable<T>`** как темы, а не как ограничения (2.6, 4.3).
- **Ковариантность и контравариантность** — почему `IEnumerable<string>` присваивается `IEnumerable<object>`, а `List<string>` нет.
- **`where T : INumber<T>`** (generic math, .NET 7+) — статические члены в интерфейсах позволяют писать обобщённые арифметические алгоритмы. До этого «сложить два `T`» было невозможно в принципе.
- **`where T : unmanaged`** — для работы с памятью напрямую.

Раздел переписан от конкретного бага: `SameCode<Enum>(Status.Draft, Color.Red)` возвращает `True`, то есть метод для сравнения внутри ОДНОГО перечисления молча сравнил значения двух РАЗНЫХ; строгая версия такой вызов не компилирует (CS0411). Добавлено следствие про `default(T)` (`null` против нулевого значения).
  Отдельно: утверждение про упаковку было НЕВЕРНЫМ по месту. Первый замер показал обратное ожидаемому (48 байт у нестрогой против 96 у строгой), потому что сравнивал не то: тело использовало `Convert.ToInt32(object)`, упаковывающий при любом ограничении, а переменная типа `Enum` была упакована один раз до цикла. Чистый замер: упаковка возникает В ТОЧКЕ ВЫЗОВА при приведении конкретного перечисления к `Enum` (48 байт/вызов), а если у вызывающего уже лежит `Enum` — цены нет. Довод понижен с первого места до третьего.
- **2026-09-22 (третья правка).** Колонка таблицы называлась «Что разрешает внутри» и содержала для `where T : struct` две разнородные вещи: операцию (`default(T)`) и утверждение о значении записи `T?`. Из-за этого строка читалась как «внутрь разрешено передать `T?`», то есть как разрешение подставить `int?` вместо `T`. Пользователь на этом и споткнулся. Колонки переименованы и разведены: вторая — каким может быть сам `T` в точке вызова, третья — что законно написать в теле. Факт про `T?` убран из ячейки в сноску и разобран в разделе про `struct`/`class`, туда же добавлено разграничение «`T` = `int?` нельзя (CS0453) / `T?` = `int?` при `T` = `int` можно» с проверкой и объяснением причины (иначе `T?` означало бы `int??`).
