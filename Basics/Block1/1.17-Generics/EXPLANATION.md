# 1.17 Дженерики: обобщённые классы и методы

Ограничения (`where T : ...`) — отдельная тема 1.18. Здесь только сам механизм: что такое параметр типа и что из этого следует.

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; **[измерено]** — есть числа замера; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

## 1. Зачем / какую проблему решает

Нужен один и тот же алгоритм (или один и тот же контейнер) для разных типов. Без дженериков вариантов два, и оба плохие.

**Вариант А — копипаста.** `IntBox`, `StringBox`, `DateTimeBox`. Одинаковый код в трёх местах, правка в одном.

**Вариант Б — `object`.** Один класс на всё, но:

```csharp
var list = new ArrayList();
list.Add(42);
string s = (string)list[0];   // компилируется. падает в рантайме
```

Две потери сразу:

1. **Ошибка переехала с компиляции на рантайм.** Компилятор про содержимое не знает ничего и возражать не может.
2. **Упаковка** (1.4). Каждый `int` уезжает в коробку на куче.

**[измерено]**, 5 000 000 элементов:

| | выделено байт | сборок Gen0 | байт на элемент |
|---|---|---|---|
| `ArrayList` | 160 000 120 | 16 | 32 |
| `List<int>` | 20 000 056 | 0 | 4 |

32 байта против 4 — это не «немного накладных расходов», это восьмикратная разница. Откуда: `ArrayList` внутри держит `object[]` — массив **ссылок** (по 8 байт), каждая указывает на отдельную коробку на куче (~24 байта). `List<int>` внутри держит `int[]` — сами числа, подряд, по 4 байта.

```
ArrayList:   [ref]--> [коробка 42]        List<int>:   [42][43][44][45]
             [ref]--> [коробка 43]                      ^ int[] — числа подряд
             [ref]--> [коробка 44]
             ^ object[]
```

*(схема на уровне «что лежит в куче»; внутренние поля `_size`/`_version` опущены — они разбирались в 1.16)*

**Дженерик — третий вариант: тип становится параметром.** Тот же класс, но кто именно лежит внутри, решает вызывающая сторона, и решает **на этапе компиляции**. Отсюда обе выгоды сразу: компилятор проверяет, упаковки нет.

Ты уже пользовался дженериками, не называя их так: `Nullable<T>` из 1.5 и `List<T>` из 1.2 — это они.

> [док] [Generics in C#](https://learn.microsoft.com/dotnet/csharp/fundamentals/types/generics)

## 2. Как устроено

### Открытый тип — это не тип

`List<>` — **определение** обобщённого типа, шаблон. Настоящий тип получается, когда параметр заполнен: `List<int>`. Первое называют открытым, второе закрытым.

**[проверено]:**

```
typeof(List<>)                                       = List`1[T]
  IsGenericTypeDefinition                            = True
typeof(List<int>)                                    = List`1[System.Int32]
typeof(List<int>) == typeof(List<string>)            -> False
одно ли у них определение (GetGenericTypeDefinition) -> True
```

Главное здесь: **`List<int>` и `List<string>` — два разных типа.** Не «один тип с разным содержимым». Разные. Из этого следует всё остальное в теме.

### Следствие 1: статическое поле своё у каждого закрытого типа

В 1.10 было: статическое поле принадлежит **типу**, а не экземпляру. Ничего не изменилось — просто типов теперь столько, сколько разных аргументов подставили.

**[проверено]:**

```csharp
class Counter<T> { public static int Count; }

Counter<int>.Count = 10;
Counter<string>.Count = 99;
Counter<double>.Count++;
```

```
Counter<int>.Count    = 10
Counter<string>.Count = 99
Counter<double>.Count = 1
```

Три независимых поля. Это и грабля, и приём: `Cache<T>.Instance` — реальный способ держать кэш, свой на каждый тип.

### Следствие 2: значимые типы получают свой машинный код, ссылочные — общий

Тело обобщённого метода компилируется в IL один раз. А вот JIT в рантайме поступает по-разному:

- **значимый аргумент** — свой машинный код на каждый. `int` (4 байта), `double` (8), `DateTime` (8) лежат в кадре по-разному, и инструкции нужны разные;
- **ссылочный аргумент** — один общий код на все. Любая ссылка одного размера, и машине всё равно, куда она указывает.

**[измерено]**, счётчик JIT-компиляций (`JitInfo.GetCompiledMethodCount()`); метод `M<T>` предварительно вызван с `Uri`, первая строка показывает цену самого измерителя:

```
(прогрев измерителя)       новых JIT-компиляций: 1
M<string>                  новых JIT-компиляций: 0
M<object>                  новых JIT-компиляций: 0
M<List<int>>               новых JIT-компиляций: 0
M<Exception>               новых JIT-компиляций: 0

M<int>                     новых JIT-компиляций: 1
M<long>                    новых JIT-компиляций: 1
M<double>                  новых JIT-компиляций: 1
M<DateTime>                новых JIT-компиляций: 1

M<int> второй раз          новых JIT-компиляций: 0
M<string> второй раз       новых JIT-компиляций: 0
```

Четыре разных ссылочных типа — ноль новых компиляций (код уже был, от `Uri`). Каждый новый значимый — одна. Повтор — ноль.

Вот отсюда и берётся отсутствие упаковки: код для `List<int>` написан JIT'ом **под `int`**, коробка ему не нужна. Это не оптимизация «по возможности», как устранение коробки в 1.16, а прямое следствие устройства.

### Что про `T` известно внутри

**Ровно ничего**, кроме того, что он тип. Это самый важный пункт темы: компилятор обязан собрать тело **один раз**, так, чтобы оно годилось для любого будущего аргумента. Значит, ничего специфического разрешить он не может.

**[проверено]**, четыре попытки и четыре отказа:

| Код внутри `<T>` | Диагностика |
|---|---|
| `new T()` | CS0304 — нет ограничения `new()` |
| `T x = null;` | CS0403 — `T` может оказаться значимым типом; нужен `default(T)` |
| `a < b` | CS0019 — оператор `<` к `T` и `T` неприменим |
| `a.Length` | CS1061 — у `T` нет `Length` |

Это не придирки компилятора, а честный ответ: он не знает, что подставят. Снимаются ограничения ровно одним способом — темой 1.18.

## 3. Синтаксис

**Обобщённый класс:**

```csharp
public class Box<T>
{
    public T Value;
    public Box(T value) => Value = value;
    public T Get() => Value;
}

var b = new Box<int>(5);       // тип указывается явно
```

**Обобщённый метод** — параметр типа у метода, а не у класса:

```csharp
public static string Pair<TA, TB>(TA a, TB b) => $"{typeof(TA).Name}/{typeof(TB).Name}";

Pair(1, "a")          // -> "Int32/String"   [проверено]
```

**Вывод типов работает у методов и не работает у конструкторов.** `Pair(1, "a")` компилятор выводит из аргументов. А вот:

```csharp
Box b = new Box(5);            // CS0305: использование универсального типа
                               // "Box<T>" требует аргументы типа 1   [проверено]
```

Отсюда распространённый приём — статический фабричный метод, чтобы не писать тип руками:

```csharp
public static class Box
{
    public static Box<T> Of<T>(T value) => new Box<T>(value);
}

var b = Box.Of(5);             // T выведен -> Box<int>
```

Обычный класс `Box` и обобщённый `Box<T>` — для компилятора разные имена, конфликта нет.

### `default` — что именно он возвращает

Правило одно, и оно проще перечисления случаев: **память под значение заполняется нулями**. Всё остальное — следствия.

```csharp
static T Def<T>() => default;     // краткая форма, тип берётся из контекста
static T Def2<T>() => default(T); // явная форма, то же самое
```

**[проверено]**, девять случаев:

| `T` | `default(T)` | Почему |
|---|---|---|
| `int`, `double` | `0` | нули в битах читаются как ноль |
| `bool` | `false` | ноль это `false` |
| `char` | символ с кодом `0` | не пробел и не пустота, а нулевой символ |
| `DateTime` | `01.01.0001 0:00:00` | нулевое число тиков |
| `string`, `object` | `null` | нулевой адрес это отсутствующая ссылка |
| `int?` | `null`, `HasValue == false` | у `Nullable<T>` флаг наличия тоже обнулён |
| `enum` | **`0`** | и это так, **даже если члена со значением 0 в перечислении нет** |
| `struct` | все поля по умолчанию, рекурсивно | у `Point { int X; string Name; bool Ok; }` получится `X=0, Name=null, Ok=false` |

Два случая заслуживают отдельного внимания.

**`enum` без нулевого члена.** Для `enum Status { Draft = 1, Active = 2 }` значение `default(Status)` равно `0`, то есть значению, которого в перечислении **не существует**: `Enum.IsDefined` для него возвращает `false` **[проверено]**. Это ровно та дыра в типобезопасности `enum`, что разбиралась в 1.7, — просто здесь в неё попадаешь не кастом `(Status)99`, а `default`.

**`struct`.** Обнуляется не сам объект целиком, а каждое поле по своему правилу, вглубь: числа в нули, ссылки в `null`. Поэтому `default` у структуры со строковым полем даст структуру с `null` внутри.

### Чего `default` не умеет

`default(T)` возвращает **обычное, совершенно законное значение типа**, а не признак отсутствия. Отличить его от того же значения, положенного намеренно, по самому значению **невозможно**:

```
default(int) == 0        -> True
default(string) == null  -> True
```

То есть «сюда ничего не клали» и «сюда положили ноль» — это один и тот же `0`. Если в задаче эти два случая надо различать, `default` для этого не годится, и признак наличия придётся хранить отдельно.

**Имена параметров** — конвенция, не правило: `T` для одного, `TKey`/`TValue`/`TResult` для нескольких, всегда с большой `T` в начале.

## 4. Грабли

**1. `null` вместо `default`.** Написать `T x = null` нельзя (CS0403): `T` может оказаться `int`. Пишется `T x = default;`.

**2. Ожидание, что `T` что-то умеет.** Сравнить, сложить, создать, взять `.Length` — ничего из этого без ограничения нельзя. Симптом: свежий обобщённый код не компилируется четырьмя ошибками подряд. Лечится темой 1.18.

**3. `List<string>` НЕ присваивается `List<object>`.**

```csharp
List<object> lo = new List<string>();   // CS0029   [проверено]
```

Первая реакция — «но строка же `object`». Верно, и именно поэтому запрещено: если бы присваивание прошло, через `lo` в список строк можно было бы положить `int`. Отсутствие такой дыры важнее удобства.

**4. Статическое поле считают общим.** `Counter<int>.Count` и `Counter<string>.Count` — разные поля (см. раздел 2). Ошибка вылезает, когда в обобщённом классе заводят счётчик «сколько всего создано».

**5. Конкретная перегрузка молча побеждает обобщённую.** Та же логика, что в 1.16: компилятор берёт наиболее конкретный подходящий метод.

**[проверено]**, рядом лежат `Which(int x)` и `Which<T>(T x)`:

```
Which(5)        -> конкретная (int)
Which(5L)       -> обобщённая (T)
Which("abc")    -> обобщённая (T)
Which<int>(5)   -> обобщённая (T)
```

Последняя строка — самая неочевидная: явное указание `<int>` **выключает** конкретную перегрузку, потому что у неё параметров типа нет вообще и под запись `Which<int>` она не подходит.

**6. Дженерик — не наследование.** `Box<int>` и `Box<string>` не родственники, друг другу не присваиваются (CS0029 **[проверено]**), общего у них только `object`.

**7. Дженерик там, где он не нужен.** `T` встречается в сигнатуре один раз и всегда подставляется одним и тем же типом — это лишний параметр, а не обобщение.

## 5. Когда что

| Ситуация | Что брать |
|---|---|
| Данные одинаковой формы, тип разный; тип нужен в нескольких членах | обобщённый **класс** `Box<T>` |
| Алгоритм разовый, состояния нет | обобщённый **метод** `Swap<T>(ref T, ref T)` |
| Внутри нужны конкретные операции над `T` | дженерик + **ограничение** (1.18) |
| Тип ровно один и меняться не будет | **не дженерик**, обычный конкретный тип |
| Нужно хранить «что угодно», и это осознанное решение | `object` — но с пониманием, чем платишь (таблица в разделе 1) |

Правило выбора «класс или метод»: параметр типа ставится там, где он **живёт**. Если `T` нужен только на время одного вызова — это параметр метода. Если `T` определяет, что лежит в объекте, — это параметр класса.

## 5б. Где встретится в реальном коде

- **`bool TryGetValue(TKey key, out TValue value)`** — связка дженериков с `out` из 1.11. Узнаётся мгновенно и встречается чаще любого другого обобщённого API.
- **`Result<T>` / `ApiResponse<T>` / `Repository<TEntity>`** в слое доступа к данным. Признак, что кто-то обобщил форму ответа. Смотреть надо, используется ли `T` больше одного раза: если нет — грабля 7.
- **Метод, не компилирующийся четырьмя ошибками CS0304 / CS0403 / CS0019 / CS1061 подряд.** Диагноз однозначный: обобщили, а ограничение не дописали. Обычно это чужой код, скопированный без строки `where`.
- **`Cache<T>.Instance` или `static readonly` внутри обобщённого класса.** Выглядит как обычная статика, работает как словарь «тип → значение». Если непонятно, почему кэш «не общий», причина здесь.
- **Замечание на ревью «зачем тут `<T>`»** — как правило, про граблю 7: обобщение без второго вызывающего.
- **Старый код с `ArrayList`, `Hashtable`, `Queue` без угловых скобок** — это .NET 1.x, до дженериков. Симптом при сопровождении: приведение типа на каждом чтении и `InvalidCastException` в логах.

| **1.10** | Статическое поле принадлежит **типу**. Механизм не изменился, изменилось число типов: `Tracked<int>` и `Tracked<string>` — два типа, значит два поля |

| **1.5** | `null` и «значения нет». `T x = null` запрещено именно потому, что `T` может оказаться значимым; `Nullable<T>` — сам по себе обобщённый тип |

## 7. Будет позже

- **1.18 — ограничения `where T : ...`**: как разрешить `T` уметь что-то конкретное.
- **Ковариантность и контравариантность** (`out T` / `in T` у интерфейсов): почему `IEnumerable<string>` всё-таки присваивается `IEnumerable<object>`, а `List<string>` — нет. Требует интерфейсов (2.2).
- **`IComparable<T>` / `IEquatable<T>`** — самые частые ограничения на практике (2.6, 4.3).
- **Обобщённые коллекции целиком** — `Dictionary<TKey, TValue>`, `HashSet<T>` и их сложность (4.1).
- **`Nullable<T>`** — уже прошли в 1.5; теперь видно, что это обычный обобщённый struct с особой поддержкой компилятора.
