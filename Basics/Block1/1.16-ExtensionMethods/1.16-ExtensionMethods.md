# 1.16 Методы расширения (extension methods)

Режим ускоренный: тема небольшая и стоит на 1.10. Задачи — `ExtensionMethods.cs`, запуск `dotnet run --project Basics -- 1.16`.

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

## 1. Зачем / какую проблему решает

Нужен метод у типа, который **изменить нельзя**: `string`, `int`, класс из чужой библиотеки, интерфейс из BCL. Обычный путь — статический помощник:

```csharp
StringHelper.Truncate(name, 10)
```

Работает, но читается наизнанку, как только вызовов становится больше одного:

```csharp
StringHelper.Capitalize(StringHelper.Trim(StringHelper.Truncate(name, 10)))
```

Метод расширения позволяет записать то же самое в порядке выполнения:

```csharp
name.Truncate(10).Trim().Capitalize()
```

Это единственная выгода — **читаемость вызова**. Никаких новых возможностей у типа не появляется.

## 2. Как устроено: это переписывание вызова, а не изменение типа

Механизм проще, чем кажется, и всё поведение темы выводится из него.

Объявление: **статический класс**, **статический метод**, первый параметр помечен `this` (всё это прямо из 1.10).

```csharp
public static class StringExtensions
{
    public static string Truncate(this string s, int max) =>
        s.Length <= max ? s : s.Substring(0, max);
}
```

Что делает компилятор, увидев `name.Truncate(10)`:

1. ищет метод `Truncate` **у самого типа** `string` — не находит;
2. ищет методы расширения в статических классах из **подключённых `using`**;
3. находит и переписывает вызов в обычный статический: `StringExtensions.Truncate(name, 10)`.

В скомпилированном коде остаётся **обычный статический вызов**. Тип `string` не изменён, ничего к нему не добавлено, никакого наследования.

Из этого следует всё остальное, включая три неочевидных вещи:

**Экземплярный метод всегда выигрывает.** Шаг 1 идёт раньше шага 2. Если у типа есть свой метод с подходящей сигнатурой, до расширения дело не дойдёт. **[проверено]**: класс со своим `Name()` и расширение `Name()` рядом — вызвался `INSTANCE`, предупреждений при сборке **ноль**.

**На `null` падает не вызов, а тело — если тело обратится к `s`.** Это статический вызов, `this` никто не разыменовывает: ссылка просто передаётся первым аргументом, и метод **входит** с `s == null`. Что будет дальше, решает автор метода.

**[проверено]**, три случая рядом:

| Что | Результат | Верхний кадр стека |
|---|---|---|
| расширение, тело НЕ трогает `s` | отработало, вернуло результат | — |
| расширение, тело трогает `s` | `NullReferenceException` | `at Ext.Trunc(...)` — **внутри метода** |
| экземплярное `nil.Length` | `NullReferenceException` | `at P.Main()` — **на строке вызова** |

Первая строка доказывает, что вызов сам по себе законен: у экземплярного члена до тела дело не доходит никогда. Третья показывает контраст — там разыменование происходит ДО входа в метод, поэтому кадр указывает на вызывающий код.

**Метод выбирается по ОБЪЯВЛЕННОМУ типу переменной.** Компилятор решает статически, как и с оператором `==` из 1.4. **[проверено]** — одна и та же строка, две переменные:

```
"abc".Describe2()             -> string-ext
object asObj = "abc";
asObj.Describe2()             -> object-ext
```

Та же мнемоника, что и для равенства: **оператор спрашивает переменную, метод спрашивает объект** — но виртуальным здесь ничего не является, поэтому и расширение «спрашивает переменную». Единственное, что спрашивает объект, — это виртуальный экземплярный метод.

> [док] Общее описание и правила разрешения: [Extension methods (C# programming guide)](https://learn.microsoft.com/dotnet/csharp/programming-guide/classes-and-structs/extension-methods)

## 3. Синтаксис

```csharp
public static class IntExtensions          // класс обязан быть static
{
    public static bool IsEven(this int n) => n % 2 == 0;   // метод static, первый параметр с this
}

// вызов
5.IsEven()
IntExtensions.IsEven(5)    // то же самое, всегда законно
```

Требования: класс `static` и не вложенный, метод `static`, `this` только у **первого** параметра.

## 4. Грабли

**1. Экземплярный метод побеждает молча.** Самая опасная. Если в будущей версии библиотеки у типа появится метод с такой же сигнатурой, твоё расширение просто перестанет вызываться — без ошибки, без предупреждения, поведение поменяется. Собирается и запускается, работает иначе.

**2. Не подключён `using` — метода «не существует».** Расширение видно только там, где подключено его пространство имён. Отсюда классическое «в документации метод есть, а у меня его нет». LINQ — это методы расширения в `System.Linq`, и без этого `using` у коллекции нет ни `Where`, ни `Select`.

**3. Выбор по объявленному типу, а не по фактическому.** Если переменная объявлена как `object`, выберется расширение для `object`, даже если внутри строка. Полиморфизма у расширений нет.

**4. `null` доезжает внутрь.** Ошибка не в момент вызова, а позже — на первом обращении к члену внутри метода. Стектрейс указывает внутрь расширения, а не на строку вызова, и это сбивает при отладке. Поэтому расширение, рассчитанное на возможный `null`, должно проверять его явно.

**5. Расширение на `object` засоряет всё.** Такой метод появится в подсказках у каждой переменной в проекте.

**6. Нельзя расширить статический класс.** У `Math` нет экземпляра, а `this`-параметру нужен объект.

**7. Доступа к закрытым членам нет.** Расширение — обычный сторонний код, `private` для него закрыт (1.8).

## 5. Когда что

| Ситуация | Решение |
|---|---|
| Чужой тип, который нельзя изменить | метод расширения |
| Интерфейс, и метод нужен всем реализациям одинаково | метод расширения |
| Свой класс, который ты контролируешь | обычный метод, не расширение |
| Нужен доступ к внутреннему состоянию | обычный метод — иначе придётся открыть состояние наружу |
| Цепочка преобразований | метод расширения, ради порядка чтения |

Правило: расширение — способ **починить чужой API**, а не способ раскидать свой по статическим классам.

## 6. Опирается на

Назвал пользователь (вопрос «что использовал»):

- **1.10 `static`** — центральная связь: метод расширения и есть статический метод в статическом классе, а `this` у первого параметра — всего лишь пометка для компилятора.
- **1.12 `StringBuilder`** — склейка в цикле внутри `Repeat`.
- **1.5 `null`** — решение про `null` в `Truncate`; `s ?? "<null>"` в `Tag` (важно: `??` **проверяет** ссылку, а не разыменовывает её, поэтому на `null` безопасен).
- **1.1 value vs reference** — `string` против `int` при выборе перегрузки.
- **1.4 boxing** — `7.Describe()` уходит в перегрузку с параметром `object`, значит значение упаковывается.
- **1.3 Stack vs Heap** — признано дублем 1.4: единственное проявление здесь — коробка, оказавшаяся в куче.

Дополнено при проверке (вопрос «что работает молча»):

- **1.8 модификаторы доступа** — расширение лежит снаружи типа и видит его как любой посторонний код: `private` для него закрыт. Это ограничение и определяет, что расширением можно сделать, а что нет; главный довод в пользу обычного метода для своего типа.
- **Разрешение на этапе компиляции по объявленному типу** — сквозной механизм темы. Он же выбирает между перегрузками для `string` и `object`, он же даёт победу экземплярному методу, он же объяснял поведение `==` на контрольной точке 1.

### Замер упаковки и ловушка самого замера

**[измерено]** 1 000 000 вызовов, Release:

| Вызов | Выделено | Gen0 | На вызов |
|---|---|---|---|
| `int.Describe()` → перегрузка с `object` | 24 000 000 байт | 2 | **24 байта** |
| `str.Describe()` → перегрузка со `string` | 0 | 0 | 0 |

24 байта — ровно размер коробки: заголовок объекта, указатель на таблицу методов и значение с выравниванием.

**Важная оговорка, полученная по ходу.** Первый вариант замера дал **0,24 байта** на вызов, то есть как будто упаковки нет вовсе. Причина: там коробка не покидала метод (результат не использовался), и JIT её не создавал. Во втором варианте коробка сохраняется в статическое поле — устранить её JIT уже не вправе.

Отсюда точная формулировка:

- **на уровне языка упаковка происходит** — компилятор обязан её вставить, это семантика;
- **будет ли реальное выделение памяти — решает JIT**; если коробка не «убегает» из метода, её может не быть.

Первый замер не отличал «упаковки нет» от «упаковка есть, но устранена оптимизацией». Второй отличает.
