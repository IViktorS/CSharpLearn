# 1.19 Атрибуты и `partial`

Последняя тема Блока 1. Обе половины — предпосылки к тому, что будет дальше: `[Fact]` в тестах (9.1) и `[ObservableProperty]` в toolkit (7.11).

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; без пометки — утверждение Claude.

> Мини-справка: **рефлексия** — возможность во время выполнения спросить у типа, что на нём написано: какие члены, какие атрибуты. Здесь нужна как чёрный ящик: `typeof(X).GetCustomAttribute<T>()` возвращает атрибут, если он есть. Отдельной темой не проходим.

## 1. Зачем / какую проблему решает

Иногда к коду нужно приписать **сведения о нём самом**, которые прочитает не человек, а другой инструмент: «этот метод — тест», «это перечисление — набор флагов», «этим свойством пользоваться больше не надо».

Без атрибутов такое передают соглашениями об именах («метод, начинающийся с `Test_`») или внешними конфигами. И то и другое разъезжается с кодом: имя переименовали, конфиг забыли.

**Атрибут — это пометка, которая живёт в самой сборке, рядом с тем, что помечает.** Переименование её не ломает, потеряться она не может.

`partial` решает другую задачу: **дать сгенерированному коду и рукописному жить в одном типе, не мешая друг другу.** Ты это уже используешь: `public partial class DataContextTree : Window` — вторую половину класса, с `InitializeComponent()`, генерирует компилятор из XAML.

## 2. Как устроено

### Атрибут — это обычный класс

`[Flags]` — не ключевое слово. Это класс `FlagsAttribute`, наследник `System.Attribute`. Суффикс `Attribute` в квадратных скобках разрешено опускать, поэтому `[Important]` и `[ImportantAttribute]` — одно и то же.

**[проверено]:**

```
тип атрибута: ImportantAttribute, наследник Attribute? True
[Important] в коде -> класс ImportantAttribute (суффикс Attribute опускается)
```

### Атрибут сам по себе не делает НИЧЕГО

Это главное в теме. Атрибут — **запись в метаданных сборки**, и не более того. Поведение появляется только тогда, когда его кто-то **читает**:

| Кто читает | Пример |
|---|---|
| компилятор | `[Obsolete]` → предупреждение при использовании |
| рантайм / библиотека класса | `[Flags]` → его читает `Enum.ToString()` |
| тестовый движок | `[Fact]` → xUnit ищет помеченные методы (9.1) |
| генератор кода | `[ObservableProperty]` → дописывает свойство (7.11) |
| твой собственный код | через рефлексию |

Ты это уже видел вживую в 1.7 и повторил на холодном входе: `[Flags]` **не меняет** битовые операции — `|`, `&`, `HasFlag` работают одинаково с ним и без него. Меняется только `ToString()`, потому что читает атрибут именно он.

**[проверено]:**

```
БЕЗ [Flags]: (a & Write)==Write -> True, HasFlag -> True, ToString() -> "3"
С  [Flags]: (a & Write)==Write -> True, HasFlag -> True, ToString() -> "Read, Write"
```

### `partial` — один тип, несколько файлов

Компилятор собирает все части в **один** тип. Ограничения: все части в одной сборке и в одном пространстве имён, у каждой должно стоять слово `partial`.

Смысл не в том, чтобы дробить большие классы (это обычно признак того, что класс делает слишком много), а в **соседстве генерируемого и рукописного**: генератор перезаписывает свой файл целиком, твой не трогает.

## 3. Синтаксис

### Свой атрибут — по шагам

**Шаг 1. Это просто класс.** Раз атрибут — класс, объявляется он как класс. Единственное, что превращает обычный класс в атрибут, — **наследование от `System.Attribute`**:

```csharp
public class ImportantAttribute : Attribute
{
}
```

Всё, атрибут готов. Его уже можно ставить: `[Important]`. Суффикс `Attribute` в скобках отбрасывается — это правило языка, а не соглашение.

**Шаг 2. Данные внутри атрибута — это обычные члены класса.** Хотим, чтобы пометка несла причину и уровень важности, — объявляем свойства и конструктор, как в любом другом классе (1.6):

```csharp
public class ImportantAttribute : Attribute
{
    public string Reason { get; }                       // задаётся только при создании
    public int Level { get; set; }                      // можно задать после
    public ImportantAttribute(string reason) => Reason = reason;
}
```

**Шаг 3. Вот главное. Запись в квадратных скобках — это описание того, как СОЗДАТЬ этот объект.**

```
[Important("ядро расчёта", Level = 3)]
 ─────────  ─────────────  ─────────
     │            │            └── присваивание свойству Level
     │            └─────────────── аргумент конструктора (параметр reason)
     └──────────────────────────── класс ImportantAttribute, суффикс отброшен
```

То есть строка читается почти буквально как:

```csharp
new ImportantAttribute("ядро расчёта") { Level = 3 }
```

Отсюда сразу оба вида аргументов, и запоминать их отдельно не надо:

| Как называется | Что это на самом деле | Откуда берётся |
|---|---|---|
| **позиционный** | аргумент конструктора | параметры конструктора атрибута |
| **именованный** | присваивание `Свойство = значение` | публичные свойства и поля атрибута |

Именованные пишутся после позиционных и в любом порядке — это тот же синтаксис объектного инициализатора, что и в 1.6.

**Шаг 4. Когда этот объект создаётся на самом деле.** Не при запуске программы. В сборке лежит **не объект, а рецепт**: какой класс, какие аргументы. Объект собирается только в момент чтения — и **каждый раз новый**.

**[проверено]**, конструктор атрибута печатает строку при выполнении:

```
1) программа стартовала, атрибут НЕ читали:
2) первое чтение через рефлексию:
   >>> конструктор атрибута выполнился
3) второе чтение:
   >>> конструктор атрибута выполнился
4) это один и тот же объект? False
```

Конструктор не выполнился ни разу, пока никто не спросил. Это и есть «атрибут сам по себе ничего не делает», только теперь видно механику.

И отсюда же становится понятно правило про константы (грабля 2): в метаданные надо записать **рецепт**, а записать туда можно лишь то, что известно на этапе компиляции. Переменную в рецепт не положишь.

**Шаг 5. `[AttributeUsage]` — пометка на пометке.** Атрибут, который вешают на свой атрибут, чтобы ограничить, где его разрешено ставить:

```csharp
[AttributeUsage(AttributeTargets.Class | AttributeTargets.Method)]
public class ImportantAttribute : Attribute { ... }
```

`AttributeTargets` — перечисление с `[Flags]` из 1.7, поэтому места перечисляются через `|`. Нарушение ловит компилятор:

```
[OnlyClass("метод")]  на методе, когда разрешены только классы
error CS0592: атрибут "OnlyClass" не допускается для этого типа объявления   [проверено]
```

Ещё два параметра: `AllowMultiple` — можно ли вешать несколько одинаковых, `Inherited` — видят ли атрибут наследники (Блок 2).

`[AttributeUsage]` не обязателен: без него атрибут можно ставить куда угодно.

**Шаг 6. Чтение.**

```csharp
var a = typeof(Engine).GetCustomAttribute<ImportantAttribute>();
// Reason="ядро расчёта", Level=3   [проверено]
```

Если атрибута нет — вернётся `null`, а не исключение.

**`partial`-метод:** объявление в одной части, реализация (необязательно) в другой.

```csharp
partial void OnStarted(int value);              // объявление
partial void OnStarted(int value) { /* ... */ } // реализация, может отсутствовать
```

Классическая форма требует `void`, без модификатора доступа и без `out`. С C# 9 разрешены и возвращаемое значение, и модификатор — но тогда **реализация обязательна**.

## 4. Грабли

**1. Атрибут без читателя не делает ничего.** Самое частое ложное ожидание: пометил — и ждёшь эффекта. Эффект появится, только если есть тот, кто эту пометку ищет.

**2. Аргументы атрибута — только константы времени компиляции.** Переменную, вычисление или объект передать нельзя.

```
[Tag(Runtime)]   // Runtime — static readonly поле
error CS0182: аргументом атрибута должно быть константное выражение,
              выражение typeof или выражение создания массива      [проверено]
```

Разрешены: литералы, `const`, `enum`, `typeof(X)` и массивы из них.

**3. `[Obsolete]` бывает двух степеней тяжести** — и по умолчанию это всего лишь предупреждение:

```
[Obsolete("скоро удалим")]            -> warning CS0618   [проверено]
[Obsolete("используй NewThing", true)] -> error   CS0619   [проверено]
```

**4. У `partial`-метода без реализации исчезает не только вызов, но и аргументы.** Компилятор вырезает всю строку целиком — включая вычисление того, что в неё передавали.

**[проверено]:** метод `Start()` вызывает `OnStarted(Compute())`, где `Compute()` увеличивает счётчик. Реализации `OnStarted` нет:

```
partial-метод без реализации: SideEffectCount = 0
```

`Compute()` не выполнился ни разу. Отсюда правило: **в аргументы `partial`-метода нельзя класть ничего, кроме вычисления самого значения** — побочный эффект оттуда просто пропадёт, молча и без следов.

**5. Все части `partial` — одна сборка и одно пространство имён.** Разнести тип по двум проектам нельзя.

## 5. Когда что

| Задача | Решение |
|---|---|
| Пометить код для внешнего инструмента | атрибут |
| Задать поведение, которое кто-то уже умеет читать | готовый атрибут (`[Flags]`, `[Obsolete]`) |
| Свой атрибут без своего читателя | не нужен — он ничего не сделает |
| Дать генератору место рядом с рукописным кодом | `partial` |
| Разбить большой класс на файлы «чтобы было меньше» | не `partial`, а разделение обязанностей |
| Точка расширения, которой может и не быть | `partial`-метод |

## 5б. Где встретится в реальном коде

Без пометки `[проверено]` — мой опыт, а не измерение.

- **Любое окно WPF.** `public partial class MainWindow : Window` — вторая половина генерируется из XAML. Если видишь `partial` без второго файла рядом — ищи генератор.
- **Тесты.** `[Fact]`, `[Theory]`, `[InlineData]` — вся разметка тестов это атрибуты, и движок находит методы именно по ним.
- **Сериализация.** `[JsonPropertyName("user_id")]` и подобное — способ развести имя в C# и имя в JSON (Блок 11).
- **`[ObservableProperty]` / `[RelayCommand]`** в CommunityToolkit.Mvvm (7.11) — атрибут плюс `partial` вместе; без `partial` генератору некуда дописать.
- **Симптом «пометил, а ничего не изменилось».** Почти всегда означает, что читателя нет: забыли пакет, не тот namespace атрибута, или атрибут вообще из другой библиотеки с похожим именем.

## 6. Опирается на

Назвал пользователь (что использовал):

- **1.5 `null`** — `attr?.Symbol ?? "-"`: у непомеченного свойства `GetCustomAttribute` возвращает `null`, и обе конструкции из 1.5 обрабатывают это одной строкой.
- **1.7 `enum` + `[Flags]`** — названо верно, но причина глубже, чем «там был пример»: **`AttributeTargets` это `[Flags]`-перечисление**, поэтому места перечисляются через `|`. Плюс сам `[Flags]` — канонический пример того, что атрибут ничего не делает без читателя.

Назвал пользователь (что работает молча) — **верно**:

- **1.6 Свойства** — запись `[Important("...", Level = 3)]` есть описание создания объекта: позиционный аргумент это параметр конструктора, именованный — присваивание свойству, то есть объектный инициализатор из 1.6.

Дополнено при проверке — три механизма в одной строке `prop.GetCustomAttribute<UnitAttribute>()`:

- **1.16 Методы расширения.** **[проверено]**: метод объявлен в статическом классе `System.Reflection.CustomAttributeExtensions` и помечен как расширение. Точечная запись работает только при `using System.Reflection` — ровно грабля 2 из 1.16 («не подключён `using` — метода не существует»).
- **1.17 + 1.18 Дженерики и ограничения.** **[проверено]**: обобщённый параметр `T` с ограничением `Attribute`, то есть `where T : Attribute`. Подставить произвольный тип не даст компилятор.
- **1.9 `readonly` vs `const`** — самая существенная из пропущенных. Различие «compile-time против runtime» здесь не иллюстрация, а **причина**, по которой `const Celsius` в аргументе атрибута законен, а `static readonly RuntimeUnit` даёт CS0182.

## 7. Будет позже

- **Рефлексия** — тема 1.20, сразу следом: обход членов типа, создание объекта по типу, цена вызова. Вторая половина того же механизма — здесь пометку ставим, там её читают.
- **Генераторы кода** (source generators) — как `[ObservableProperty]` превращается в свойство (7.11).
- **`[CallerMemberName]` и друзья** — атрибуты, которые заполняет компилятор; основной приём в реализации `INotifyPropertyChanged` (7.6).
- **`[AttributeUsage(Inherited = ...)]`** — как атрибуты ведут себя при наследовании (Блок 2).

- **2026-09-29.** Раздел «Свой атрибут» был свалкой: объявление, `AttributeUsage`, позиционные и именованные аргументы, отбрасывание суффикса — всё разом, в одном примере, без объяснения, что откуда. Пользователь на нём встал. Переписан по шагам, вокруг одной опорной мысли: **запись в квадратных скобках это описание того, как создать объект атрибута**, то есть почти буквально `new ImportantAttribute("...") { Level = 3 }`. Из неё выводятся оба вида аргументов (позиционный = параметр конструктора, именованный = присваивание свойству), и не нужно запоминать их отдельно. Добавлен замер момента создания: конструктор атрибута НЕ выполняется при запуске программы, выполняется при каждом чтении рефлексией, и объект каждый раз новый — отсюда же понятно правило про константы (в метаданных лежит рецепт, а не объект). Добавлен CS0592 на нарушение `AttributeUsage`.
