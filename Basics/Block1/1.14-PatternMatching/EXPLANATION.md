# 1.14 Pattern matching (`switch`-выражения, `is`-паттерны, property patterns)

## 1. Зачем / какую проблему решает

Очень частая связка в коде: **проверить → извлечь → использовать**. До паттернов она писалась в три шага:

```csharp
object o = 42;

if (o is int)          // 1. проверили тип
{
    int n = (int)o;    // 2. распаковали — ВТОРАЯ проверка типа в рантайме
    Console.WriteLine(n + 1);
}
```

Здесь две проблемы. Во-первых, работа делается дважды: `is` проверяет тип коробки, потом каст проверяет его же ещё раз. Во-вторых, проверка и распаковка разъезжаются по коду — правишь одну, забываешь вторую, и получаешь `InvalidCastException` из темы 1.4.

Вторая проблема — лестницы. Когда вариантов много, `if/else if/else if` разрастается, и в каждой ветке повторяется одно и то же имя переменной. Ошибиться в порядке условий или потерять ветку легко, а компилятор молчит.

**Паттерн-матчинг решает оба случая:** проверка и извлечение становятся одной конструкцией, а набор вариантов — одним выражением, полноту которого компилятор умеет проверять.

```csharp
if (o is int n)                    // проверил И достал, одной строкой
    Console.WriteLine(n + 1);
```

## 2. Как устроено

**Паттерн — это не выражение, а шаблон**, с которым сопоставляется значение. У сопоставления два результата:

1. подошло или нет (`bool`);
2. если подошло — могут появиться **новые переменные**, уже заполненные данными из проверенного значения.

Второй пункт — вся суть. `o is int n` не просто отвечает «да»: при успехе он объявляет `n` и кладёт туда распакованное значение. Это ровно **безопасная версия каста из темы 1.4**: там несовпадение типа давало исключение, здесь оно даёт `false`.

Правило точности типа при этом никуда не делось — оно то же самое, что при распаковке:

```csharp
object o = 5;          // в коробке int
o is long              // false! не «5 влезает в long», а «в коробке не long»
```

Переменная паттерна **видна дальше по коду** — в той ветке, где сопоставление истинно:

```csharp
if (o is int n)
    Console.WriteLine(n);   // n доступна
// здесь n уже нет смысла: сопоставление могло не сработать
```

Компилятор следит за этим через определённое присваивание: если он не может доказать, что `n` заполнена, будет **CS0165** («использование локальной переменной, которой не присвоено значение»).

## 3. Синтаксис

### Виды паттернов

| Паттерн | Пример | Что делает |
|---|---|---|
| Константный | `is 0`, `is "hello"`, `is Status.Active` | сравнивает со значением |
| `null` | `is null`, `is not null` | проверка на null (тема 1.5) |
| Тип с объявлением | `is int n`, `is string s` | проверяет тип И заводит переменную |
| Тип без объявления | `is int` | только проверка |
| Реляционный | `is > 0`, `is <= 100` | сравнение с константой |
| Логический | `is > 0 and < 10`, `is not null` | комбинация: `and`, `or`, `not` |
| Свойств (property) | `is { Length: 0 }` | проверяет значения свойств |
| Кортежный (tuple) | `is (0, 0)` | разбирает кортеж по позициям (тема 1.13) |
| Списочный (list) | `is [1, 2, 3]`, `is [_, _, ..]` | разбирает массив/список по форме |
| `var` | `is var x` | всегда истинен, просто даёт имя |
| Discard | `_` | «что угодно, значение не нужно» (тема 1.13) |

### `switch`-выражение

```csharp
string label = n switch
{
    < 0          => "отрицательное",
    0            => "ноль",
    > 0 and < 10 => "маленькое",
    _            => "большое"
};
```

Отличия от привычной `switch`-инструкции:

- это **выражение** — оно возвращает значение, его можно присвоить или вернуть из метода;
- значение слева от `switch`, а не в скобках после него;
- `=>` вместо `case ... :`, запятая вместо `break`;
- `_` вместо `default`;
- **ветви проверяются сверху вниз, срабатывает первая подошедшая.**

### Паттерн свойств

Работает с любыми свойствами (тема 1.6) и вкладывается:

```csharp
p is { Name.Length: > 3, Age: >= 18 and < 65 }
```

Читается как «у `p` длина `Name` больше 3 И `Age` в диапазоне». Проверка на `null` встроена: если `p` равен `null`, паттерн просто даёт `false`, без падения.

### `when` — досыл условия

Когда нужна проверка, которую паттерном не выразить (например, связь двух значений между собой):

```csharp
(a, b) switch
{
    var (x, y) when x == y => "равны",
    (0, _)                 => "первый ноль",
    _                      => "разные"
}
```

## 4. Грабли

**1. Порядок ветвей значим — и неудачный порядок это ошибка, а не предупреждение.**
Первая подошедшая ветвь выигрывает. Если широкий паттерн стоит выше узкого, до узкого дело никогда не дойдёт, и компилятор скажет **CS8510** («шаблон является недоступным») — именно `error`, сборка не пройдёт.

```csharp
n switch
{
    _   => "любое",          // съедает всё
    > 0 => "положительное",  // CS8510: недостижимо
}
```

**2. Неполнота — это всего лишь предупреждение, а падает уже в рантайме.**
Если ни одна ветвь не подошла, `switch`-выражение бросает `SwitchExpressionException`. Компилятор предупреждает заранее — **CS8509** («выражение switch не обрабатывает все возможные типы входных значений») — но это `warning`, и собраться оно не мешает.

Асимметрия, которую стоит запомнить:

| Что сделал | Код | Чем оборачивается |
|---|---|---|
| Написал **лишнее** (недостижимая ветвь) | CS8510 | `error` — сборка падает |
| **Забыл** случай (неполный switch) | CS8509 | `warning` — падает рантайм |

Компилятор жёстко ловит первое и лишь бормочет про второе — притом что второе опаснее.

**3. Отдельная ловушка — `enum`, и она прямо из темы 1.7.**
Перечислить все именованные значения `enum` **недостаточно**: в переменной может лежать число вне диапазона (`(Status)99` хранится и живёт, как мы видели). Компилятор это знает и выдаёт отдельный код — **CS8524**, с текстом про «неименованное значение перечисления». Лечится веткой `_`.

**4. Переменная паттерна внутри `or` и `not` бесполезна — но ломается по-разному.**

Общая причина одна: переменная обязана быть **определённо присвоена** там, где ею пользуются (то же правило, что и CS0165 выше). В обоих случаях компилятор не может этого гарантировать, но реагирует по-разному:

```csharp
o is int n or long     // CS8780 — объявить нельзя вообще, сразу ошибка
                       // (сработала вторая альтернатива → заполнять n нечем)

o is not int n         // компилируется, пока n не трогаешь!
                       // но любое использование n → CS0165
                       // (паттерн истинен ровно тогда, когда o НЕ int → n заполнить нечем)
```

`not` коварнее: код собирается, ошибка вылезает только когда переменную попробуешь применить.

**5. `is not null` надёжнее, чем `!= null`.**
Оператор `!=` может быть **перегружен** типом, и тогда он сделает что угодно — мы это уже видели с `==` у `string` на контрольной точке 1. Паттерн `is` перегрузить нельзя: он всегда спрашивает про настоящий `null`.

**6. Паттерн только читает — починить им мутацию struct нельзя.**
`list[0] is { Value: 1 }` читает **копию** элемента (индексатор `List<T>` возвращает копию — тема 1.2). Паттерны ничего не присваивают, так что обойти CS1612 через них не получится.

**7. `int?` со значением `null` не проходит `is int`.**
```csharp
int? q = null;
q is int n     // false
```
Логично: значения нет, брать в `n` нечего.

## 5. Когда что

| Ситуация | Что писать |
|---|---|
| Одна проверка типа + сразу использование | `if (o is int n)` |
| Несколько взаимоисключающих вариантов → **значение** | `switch`-выражение |
| Несколько вариантов → **действия** в несколько строк | `switch`-инструкция с паттернами |
| Проверка «не null» | `is not null` |
| Попадание в диапазон | `is >= 1 and <= 9` |
| Условие сразу по нескольким свойствам объекта | паттерн свойств `is { A: ..., B: ... }` |
| Разбор кортежа по вариантам | кортежный паттерн |
| Условие, которое паттерном не выразить | ветвь с `when` |

Обратная сторона: паттерн, у которого больше двух-трёх уровней вложенности, читается хуже обычного `if`. Цель — короче и понятнее, а не «уместить всё в один `switch`».

## 7. Будет позже

- **Паттерны по типам-наследникам и интерфейсам** (`is Dog d`) — главный сценарий паттерн-матчинга в реальном коде, но он требует наследования: Блок 2 (2.1–2.3).
- **Позиционные паттерны** `is Point(0, 0)` — работают через метод `Deconstruct` (его мы уже писали в 1.13) и особенно удобны с `record`: тема 2.7.
- **`switch` по типам вместо `virtual`-метода** — где паттерн уместен, а где это признак пропущенного полиморфизма: Блок 2.
