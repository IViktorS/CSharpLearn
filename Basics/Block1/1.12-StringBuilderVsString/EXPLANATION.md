# 1.12 StringBuilder vs string — и строка как объект

Задачи — `StringBuilderVsString.cs`, запуск `dotnet run --project Basics -- 1.12`.

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; **[измерено]** — есть числа замера; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

Конспект переписан 2026-10-01 в текущем формате (см. «Изменения конспекта» внизу). Разделы 4–6 про равенство и интернирование — новые: эти механизмы разбирались на 1.17 и в разборе очереди №1, но в конспекте их не было.

## 1. Зачем / какую проблему решает

`string` **иммутабельна**: созданную строку изменить нельзя. Любая операция, которая выглядит как изменение, создаёт **новую** строку, а исходная остаётся как была.

**[проверено]**:

```
s = привет, s.ToUpper() = ПРИВЕТ, тот же объект? False
```

Для пары склеек это незаметно. Для склейки в цикле — катастрофа, и `StringBuilder` существует ровно затем, чтобы её не было.

> [док] [String class — Immutability](https://learn.microsoft.com/dotnet/api/system.string#immutability-and-the-stringbuilder-class)

## 2. Как устроено

### Почему склейка в цикле дорогая

```csharp
string result = "";
for (int i = 0; i < N; i++) result += "x";
```

На каждой итерации создаётся **новая** строка, и в неё **копируется всё предыдущее** содержимое плюс один символ. Старая уходит в мусор. Длины строк — 1, 2, 3, …, N, и суммарный объём копирования растёт как N².

**[измерено]**, 30 000 итераций:

| | выделено байт | сборок Gen0 |
|---|---|---|
| `string +=` | **900 779 976** | 95 |
| `StringBuilder` | **125 344** | 0 |

900 миллионов байт — это ровно квадратичный рост, посчитанный напрямую: сумма длин 1 + 2 + … + 30 000 ≈ 450 миллионов символов, по 2 байта на символ. Цифра не «много», а **предсказуемая**: удвоишь N — получишь вчетверо больше.

### StringBuilder — изменяемый буфер

`StringBuilder` держит буфер с запасом и дописывает в него **на месте**, без новых строк. Строка создаётся один раз — при вызове `ToString()`.

**[проверено]**, как растёт ёмкость при дописывании по одному символу:

```
Capacity: 16 → 32 → 64 → 128 → 256 → 512
```

Ёмкость удваивается, поэтому расширений мало даже на больших объёмах.

### Строка — ссылочный тип со своим равенством

Это вторая половина темы, и в ней больше граблей, чем в первой.

`string` — **ссылочный** тип (1.1): переменная хранит ссылку на объект в куче. Значит, у двух строк с одинаковым текстом есть **два разных вопроса**:

1. **Одинаковое ли содержимое?** — `==` и `Equals`.
2. **Один ли это объект в памяти?** — только `ReferenceEquals`.

Ответы на них расходятся, и путать их — главная ошибка темы.

**[проверено]**, у всех переменных текст «привет», сравнение с `a = "привет"`:

| Как получена строка | `==` | `Equals` | `ReferenceEquals` |
|---|---|---|---|
| второй литерал `"привет"` | True | True | **True** |
| `new string(...)` | True | True | False |
| `half + "вет"`, где `half` — переменная | True | True | False |
| `"при" + "вет"` — два литерала | True | True | **True** |
| `halfConst + "вет"`, где `halfConst` — `const` | True | True | **True** |
| `new StringBuilder("привет").ToString()` | True | True | False |
| `string.Intern(new string(...))` | True | True | **True** |

Столбцы `==` и `Equals` — сплошь `True`: текст везде одинаковый. Вся интересная информация в последнем столбце.

### Почему `==` сравнивает содержимое — и когда перестаёт

Для `object` оператор `==` сравнивает **ссылки** (1.4). Для `string` он **перегружен** и сравнивает **содержимое**. Какой из двух операторов применить, компилятор решает по **объявленному типу переменной**, а не по тому, что лежит в ней на самом деле.

**[проверено]**, одни и те же два объекта, `a` — литерал, `c` — `new string(...)`:

```
string a == string c   : True
object oa == object oc : False
oa.Equals(oc)          : True
```

Объекты не менялись — поменялся только тип переменных, и `==` стал другим оператором. А `Equals` дал `True` в обоих случаях: это метод, и он спрашивает сам объект, а объект — строка.

Мнемоника из 1.4: **оператор спрашивает переменную, метод спрашивает объект.**

Если с одной стороны `object`, а с другой `string`, компилятор предупреждает — **[проверено]**:

```
warning CS0252: Возможно, непреднамеренное сравнение ссылок;
                для получения сравнения значений приведите левую часть к типу "string".
```

### Интернирование литералов

Одинаковые строковые **литералы** в сборке — это **один объект**. Компилятор и рантайм складывают их в общий пул («интернируют») и раздают одну ссылку на всех. Поэтому два независимо написанных `"привет"` дают `ReferenceEquals == True`.

Строка, **собранная при выполнении** — через `new string`, склейку с переменной, `StringBuilder.ToString()`, чтение из файла, — в пул не попадает. Это новый объект, даже если текст совпал до символа.

Положить такую строку в пул можно вручную: `string.Intern(s)` вернёт ссылку на объект из пула (последняя строка таблицы).

### Свёртка констант: склейка, которой нет

`"при" + "вет"` выглядит как склейка, но при выполнении её **не происходит**. Обе части — константы, их значение известно уже при компиляции, и компилятор склеивает их сам. В сборку попадает готовый литерал `"привет"` — тот же, что у `a`, а дальше срабатывает интернирование.

То же самое с `const` — прямое продолжение 1.9: `const` вычисляется при компиляции и подставляется на место. А вот обычная переменная `half` известна только при выполнении, поэтому `half + "вет"` — настоящая склейка в рантайме и новый объект.

Правило: **«новая строка при каждой операции» верно для рантайма.** Если операцию выполнил компилятор, в рантайме никакой операции нет.

## 3. Синтаксис

```csharp
var sb = new StringBuilder();
sb.Append("текст").Append(42).AppendLine();
sb.Insert(0, ">> ");
sb.Replace("текст", "слово");
sb.Remove(0, 3);
sb.Clear();
string result = sb.ToString();
```

`Append` возвращает тот же `StringBuilder`, поэтому вызовы сцепляются.

`string.Join(sep, values)` ставит разделитель **только между** элементами и обрабатывает всю коллекцию за один вызов — **[проверено]**: `string.Join(", ", ["a", "b", "c"])` → `[a, b, c]`.

## 4. Грабли

**1. Склейка в цикле.** `+=` в цикле с неизвестным числом итераций — квадратичный рост (см. замер выше).

**2. `==` через `object`.** Строки, лежащие в переменных типа `object` (или в коллекции `object`), сравниваются по ссылкам. Две строки с одинаковым текстом дадут `False`. Признак — предупреждение CS0252.

**3. Полагаться на `ReferenceEquals` для строк.** Интернирование — деталь реализации, а не часть логики. Сегодня строка пришла литералом и совпала по ссылке, завтра её прочитают из файла — и не совпадёт. Сравнение строк в логике — всегда `==` или `Equals`, никогда `ReferenceEquals`.

**4. «Изменить» строку и забыть присвоить.** `s.ToUpper();` без присваивания ничего не делает: результат — новая строка, и она выброшена. Нужно `s = s.ToUpper();`.

**5. `StringBuilder` везде.** Для `$"{name}: {age}"` или двух-трёх склеек обычная строка читается лучше и не медленнее. `StringBuilder` нужен там, где число операций заранее неизвестно.

## 5. Когда что

| Ситуация | Что брать |
|---|---|
| пара склеек, число известно | `+` или интерполяция `$"..."` |
| склейка в **цикле**, число неизвестно | `StringBuilder` |
| соединить готовую коллекцию | `string.Join(sep, values)` |
| сравнить **текст** | `==` (у переменных типа `string`) или `Equals` |
| узнать, **один ли объект** | `ReferenceEquals` — для диагностики, не для логики |

## 5б. Где встретится в реальном коде

- **Сборка отчёта или CSV в цикле через `+=`** — классическое замечание на ревью. Симптом в работе: экспорт тормозит непропорционально объёму, вдвое больше строк — вчетверо дольше.
- **Предупреждение CS0252 в коде с `object`** — чаще всего сравнение элемента необобщённой коллекции или свойства типа `object` со строкой. Это настоящий баг, а не шум: такое сравнение почти всегда хотело сравнить текст.
- **Сравнение, которое «работает в тестах и не работает в бою».** В тесте строки — литералы и совпадают по ссылке, в бою они приходят из базы или файла. Если в коде есть `ReferenceEquals` или сравнение через `object`, причина там.
- **`string.Intern` в чужом коде** — редкость; встречается, когда нужно сэкономить память на миллионах одинаковых строк. Если видишь его в обычной бизнес-логике, это повод спросить зачем.

## 7. Будет позже

- **Сравнение строк с учётом культуры и регистра** — `StringComparison.Ordinal`, `OrdinalIgnoreCase`, `CurrentCulture`. Связано с 11.4 (`CultureInfo`).
- **`IEquatable<T>` и переопределение `Equals`** (2.6) — как сделать для своего типа то, что `string` делает для себя: равенство по содержимому.
- **Кодировки** (11.3) — откуда 2 байта на символ и почему в файле их бывает другое число.
- **`Span<char>`, `string.Create`** — способы работать с текстом вообще без лишних выделений. Анонс, отдельной темы нет.
