# 2.1 Инкапсуляция, наследование, полиморфизм

Первая тема Блока 2. Формат другой: предсказаний нет, задача — **типа 2** («вот требование — напиши, потом разбираем развилки»). Перед ней — 2–3 вопроса на понимание механизма (шаг 2 цикла).

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

## 1. Зачем / какую проблему решает

«Три кита ООП» обычно заучивают как лозунг. Полезнее читать их как ответы на три вопроса о коде, который будет меняться:

| Принцип | На какой вопрос отвечает | Что ломается без него |
|---|---|---|
| **Инкапсуляция** | кто вправе менять состояние объекта? | правило вроде «уровень не бывает отрицательным» держится, только пока все его соблюдают |
| **Наследование** | как не повторять общее у похожих типов? | одинаковый код в пяти классах и правка в пяти местах |
| **Полиморфизм** | как одному и тому же вызывающему коду работать с разными типами, не зная их? | каждый вызывающий код перечисляет все типы сам, и новый тип требует правки везде |

Ты уже пользовался всеми тремя, не называя их:

- **инкапсуляция** — `private set` и проверки в сеттере (1.6), модификаторы доступа (1.8);
- **наследование** — каждое окно задач WPF-трека объявлено как `public partial class BindingModes : Window`: окно — наследник `Window`;
- **полиморфизм** — в `App.xaml.cs` раннер написан как `protected override void OnStartup(...)`, а у `Person` из 7.3 был `override string ToString()`.

## 2. Как устроено

### Инкапсуляция — это про инвариант, а не про `private`

**Инвариант** — правило, которое объект гарантирует про себя сам: «уровень от 0 до объёма», «у заказа есть хотя бы одна позиция». Инкапсуляция — это устройство, при котором нарушить правило снаружи **невозможно**: состояние закрыто, а менять его можно только через методы, которые правило проверяют.

```csharp
public class Tank
{
    private double _level;                       // закрыто: напрямую не поменять
    public double Capacity { get; }
    public double Level => _level;               // читать — можно всем

    public Tank(double capacity) => Capacity = capacity;

    public void Fill(double amount)              // менять — только так
    {
        if (amount < 0 || _level + amount > Capacity)
            throw new ArgumentOutOfRangeException(nameof(amount));
        _level += amount;
    }
}
```

**[проверено]**: `new Tank(100)`, `Fill(30)` → `Level = 30`; затем `Fill(80)` отклонён исключением, `Level` остался 30 — правило «не больше объёма» не нарушить.

`private` здесь — средство, а не цель. Если в классе есть открытый сеттер `Level { get; set; }`, то `private`-поле ничего не охраняет. И помни оговорку из 1.8: модификаторы проверяет компилятор, и рефлексия (1.20) их обходит. Инкапсуляция — контракт между частями кода, а не защита от умысла.

### Наследование и полиморфизм — на трёх опытах

Всё, что ниже помечено **[проверено]**, получено на трёх небольших программах. Каждая показана целиком, вывод снят именно с неё.

#### Опыт 1: что видит наследник и в каком порядке создаётся объект

```csharp
public class Device
{
    private string _serial = Log("Device: инициализатор поля _serial");
    public string Name { get; }

    public Device(string name)
    {
        Log("Device: тело конструктора");
        Name = name;
        Log($"Device: вызываю виртуальный Describe() -> {Describe()}");
    }

    public virtual string Describe() => $"устройство {Name}";

    public static string Log(string s) { Console.WriteLine(s); return s; }
}

public class Pump : Device
{
    private string _fromInitializer = Log("Pump: инициализатор поля _fromInitializer");
    private string _fromConstructor;

    public Pump(string name) : base(name)
    {
        Log("Pump: тело конструктора");
        _fromConstructor = "задано";
    }

    public override string Describe() =>
        $"насос {Name}, _fromInitializer={(_fromInitializer is null ? "null" : "заполнено")}, _fromConstructor={_fromConstructor ?? "null"}";
}

// запуск
var pump = new Pump("Н-1");
Console.WriteLine($"после создания: {pump.Describe()}");
// и рефлексией (1.20) — закрытое поле базового класса у объекта наследника:
typeof(Device).GetField("_serial", BindingFlags.NonPublic | BindingFlags.Instance)!.GetValue(pump);
```

`Log` — вспомогательный метод: печатает строку и возвращает её. Им инициализированы поля, чтобы увидеть момент инициализации.

**[проверено]**, вывод:

```
Pump: инициализатор поля _fromInitializer
Device: инициализатор поля _serial
Device: тело конструктора
Device: вызываю виртуальный Describe() -> насос Н-1, _fromInitializer=заполнено, _fromConstructor=null
Pump: тело конструктора
после создания: насос Н-1, _fromInitializer=заполнено, _fromConstructor=задано
закрытое _serial класса Device у объекта Pump: «Device: инициализатор поля _serial»
```

Из этого опыта три вывода.

**Объект один.** `Pump` получил все члены `Device`, и закрытое поле `_serial` физически живёт внутри объекта `Pump` — рефлексия его прочитала. Обратиться к нему из кода `Pump` при этом нельзя (опыт 3).

**Порядок создания: инициализаторы полей идут от наследника к базовому, тела конструкторов — от базового к наследнику.** Это первые четыре строки вывода. Тело конструктора `Device` выполняется, когда тело конструктора `Pump` ещё не начиналось.

**Виртуальный вызов из конструктора базового попадает в недостроенного наследника.** Четвёртая строка: конструктор `Device` позвал `Describe()`, ответила версия `Pump`, и у неё `_fromInitializer` уже заполнено, а `_fromConstructor` — ещё `null`. После создания то же поле уже `задано`. Подробнее — грабля 1.

#### Опыт 2: какую версию метода выберет вызов

`Describe` и `Kind` — методы, придуманные для опыта. Оба просто возвращают строку-метку, по которой в выводе видно, **чья версия ответила** на вызов. Разница между ними одна: `Describe` в `Device` помечен `virtual`, а `Kind` — обычный метод. `Kind` здесь контрольный образец: он показывает, что было бы с `Describe` без `virtual`.

```csharp
public class Device
{
    public string Name { get; }
    public Device(string name) => Name = name;

    public virtual string Describe() => $"устройство {Name}";   // можно переопределить
    public string Kind() => "Device.Kind";                       // обычный метод
    public override string ToString() => $"Device({Name})";
}

public class Pump : Device
{
    public Pump(string name) : base(name) { }

    public override string Describe() => $"насос {Name}";       // переопределение
    public new string Kind() => "Pump.Kind";                     // сокрытие — тема 2.3
}

public class Sensor : Device
{
    public Sensor(string name) : base(name) { }
    public override string ToString() => $"Sensor({Name})";
}

// запуск
var pump = new Pump("Н-1");
Device d = pump;
object o = new Sensor("Д-7");
```

**[проверено]**, вывод:

```
ReferenceEquals(d, pump) → True
d.GetType().Name         → Pump
d is Pump                → True
d.Describe()             → насос Н-1
d.Kind()                 → Device.Kind
pump.Kind()              → Pump.Kind
Console.WriteLine(o)     → Sensor(Д-7)
```

**Наследник «является» базовым.** Переменная типа `Device` хранит объект `Pump` — **ту же ссылку на тот же объект**, без копии и без преобразования (1.1). `GetType()` спрашивает объект и отвечает `Pump` (1.20); `is` (1.14) — тоже.

**Виртуальный метод спрашивает объект, обычный — переменную.** `Describe()` помечен `virtual` и переопределён через `override`: вызов через `d` ушёл в версию `Pump`, потому что объект — `Pump`. `Kind()` обычный: вызов через `d` ушёл в версию `Device`, потому что переменная — `Device`. Это и есть полиморфизм: версия выбирается по **фактическому типу объекта**, но только у виртуальных методов.

Мнемоника из 1.4 — «оператор спрашивает переменную, метод спрашивает объект» — получает точную форму: **объект спрашивает виртуальный метод.** Обычный метод выбирается по объявленному типу переменной — как оператор `==` (1.4) и метод расширения (1.16).

Отсюда же давний факт про `Equals`: он — **виртуальный** метод класса `object`, поэтому и «спрашивает объект». То же с `ToString` — последняя строка вывода: переменная объявлена как `object`, а напечаталось `Sensor(Д-7)`.

У класса в C# может быть только **один** базовый класс. Как получить «несколько ролей» у одного типа — тема 2.2.

#### Опыт 3: что компилятор не пропустит

```csharp
public class Device
{
    private int _hours;                                      // закрытое поле
    public string Name { get; }
    public Device(string name) { Name = name; _hours = 0; }
    public string Describe() => "устройство";               // НЕ virtual
    public string Kind() => "Device";
}

public class Valve : Device { }                              // (1) конструктора нет вовсе

public class Gauge : Device
{
    public Gauge(string name) : base(name) { }
    public override string Describe() => "датчик";          // (2) override не-virtual метода
    public string Kind() => "Gauge";                         // (3) тот же метод, без new
    public int Read() => _hours;                             // (4) закрытое поле базового
}

// где-то в коде
var g = new Gauge();                                         // (5) конструктора без параметров нет
```

**[проверено]** двумя сборками: об ошибках в объявлениях компилятор сообщает раньше, чем об ошибках в телах методов, поэтому строка (2) проверялась отдельно.

| | Результат |
|---|---|
| (1) | `error CS7036`: отсутствует аргумент для параметра `name` из `Device.Device(string)` |
| (2) | `error CS0506`: невозможно переопределить `Device.Describe()`, он не помечен как `virtual` |
| (3) | `warning CS0108`: `Gauge.Kind()` скрывает `Device.Kind()`; если намеренно — используйте `new` |
| (4) | `error CS0122`: `Device._hours` недоступен из-за уровня защиты |
| (5) | `error CS7036`: отсутствует аргумент для параметра `name` из `Gauge.Gauge(string)` |

- **Конструкторы не наследуются** — (1) и (5). Наследник обязан вызвать конструктор базового через `: base(...)`. Если у базового нет конструктора без параметров, а наследник его не вызывает, ошибка стоит прямо на объявлении класса.
- **Без `virtual` переопределить нельзя** — (2).
- **Тот же метод без `override` — не ошибка, а предупреждение** — (3). Сборка проходит, а поведение тихо другое: через переменную базового типа вызовется версия базового, как `d.Kind()` в опыте 2. Грабля 2.
- **`private` базового закрыт для наследника** — (4), клетка «`private` / наследник» из таблицы 1.8.

## 3. Синтаксис

```csharp
public class Device
{
    public string Name { get; }
    protected Device(string name) => Name = name;      // protected: создавать могут только наследники (1.8)

    public virtual string Describe() => $"устройство {Name}";
}

public class Pump : Device
{
    public double Pressure { get; }

    public Pump(string name, double pressure) : base(name)   // сначала конструктор Device
        => Pressure = pressure;

    public override string Describe()
        => base.Describe() + $", давление {Pressure}";        // base. — вызвать версию базового
}
```

**[проверено]**: `Device d = new Pump("Н-1", 4); d.Describe()` → `устройство Н-1, давление 4`.

`base.Describe()` вызывает версию базового класса изнутри переопределения — так расширяют поведение, а не заменяют его целиком. Ровно это делает `base.OnStartup(e)` в `App.xaml.cs`.

### Разбор записи `: base(...)`

```csharp
public Gauge(string name) : base(name) { }
```

| Часть | Что значит |
|---|---|
| `public Gauge(string name)` | конструктор класса `Gauge`, принимает строку `name` |
| `: base(name)` | **до** тела этого конструктора вызвать конструктор **базового** класса и передать ему `name` |
| `{ }` | тело конструктора `Gauge` — пустое: самому `Gauge` настраивать нечего |

Читается так: «чтобы создать `Gauge`, сначала создай его часть `Device` вот с этим аргументом». Конструкторы не наследуются (опыт 3), поэтому наследник обязан сказать, какой конструктор базового вызвать и с чем.

Если `: base(...)` не написать, компилятор сам подставит `: base()` — вызов **без параметров**. Проверено на таких классах:

```csharp
public class Device
{
    public string Name { get; }
    public Device() { Console.WriteLine("  Device() — без параметров"); }   // этой строки может не быть
    public Device(string name) { Console.WriteLine($"  Device(\"{name}\")"); Name = name; }
}

public class Gauge : Device
{
    public Gauge(string name) : base(name) { Console.WriteLine("  тело Gauge"); }
}

public class Forgot : Device
{
    public Forgot(string name) { Console.WriteLine("  тело Forgot"); }     // : base(name) забыт
}
```

**[проверено]**, два исхода:

| У `Device` | `new Forgot("Д-2")` |
|---|---|
| нет конструктора без параметров | `error CS7036`: отсутствует аргумент для параметра `name` из `Device.Device(string)` — сборка не проходит |
| есть конструктор без параметров | сборка проходит, вывод ниже |

```
new Gauge("Д-1"):
  Device("Д-1")
  тело Gauge
  -> Name = Д-1
new Forgot("Д-2"):
  Device() — без параметров
  тело Forgot
  -> Name = null
```

Второй исход хуже первого. Аргумент `"Д-2"` дошёл до `Forgot` и пропал: никто не передал его в `Device`, `Name` остался `null`, а компилятор молчит — формально всё законно.

## 4. Грабли

**1. Виртуальный вызов из конструктора базового класса попадает в недостроенного наследника.** Опыт 1, четвёртая строка вывода: конструктор `Device` вызвал виртуальный `Describe()`, ответила версия `Pump`, а поле, которое задаёт тело конструктора `Pump`, — ещё `null`: до этого тела дело не дошло. Поле с инициализатором при этом уже заполнено, потому что инициализаторы наследника выполняются первыми. Код наследника работает с объектом, который сам считает невалидным.

**2. Забыли `override` — получили сокрытие, и только предупреждение.** Опыт 3, строка (3): `warning CS0108`, сборка проходит. А поведение другое: через переменную базового типа вызывается версия базового (опыт 2, `d.Kind()`). Подробно — 2.3.

**3. Конструкторы не наследуются** (опыт 3, строки (1) и (5)). Добавил в базовый класс обязательный параметр конструктора — сломались все наследники.

**4. `protected` ослабляет инкапсуляцию.** Поле `protected` может поменять **любой** наследник, в том числе написанный завтра другим человеком. Инвариант базового класса держится тогда не на базовом классе, а на дисциплине всех наследников.

**5. Наследование ради переиспользования кода, а не ради «является».** Если `Pump : Logger` только затем, чтобы получить метод `Log`, — насос не является журналом. Такое наследование тянет за собой всё, что есть у базового класса. Альтернатива — тема 2.5.

## 5. Когда что

| Ситуация | Что брать |
|---|---|
| правило про состояние объекта должно держаться всегда | закрытое состояние + методы, проверяющие правило |
| у нескольких типов общие данные и общее поведение, и каждый **является** общим | базовый класс |
| одно действие, у каждого типа своё поведение, вызывающий код не должен знать типы | виртуальный метод |
| одно действие, у каждого типа своё поведение, но решение принимает вызывающий код | выбор по типу (`switch` с паттернами, 1.14) |
| нужен чужой код, но отношения «является» нет | не наследование — 2.5 |

Между двумя средними строками — настоящая развилка, и у каждого варианта своя цена. Её и разбирает задача. Итог разбора — ниже.

### Итог разбора задачи: виртуальный метод против выбора по типу

Записано после разбора задачи 2.1 (2026-10-21). Решение пользователя хранило устройства в `List<object>` внутри `ControlRoom<object>` и выбирало строку через `switch` по типу, а каждая ветка вызывала… виртуальный `GetDescription()`. То есть полиморфизм был построен и затем обойдён вручную.

**[проверено]** на классах из решения пользователя (`Pump`, `GateValve`, `TemperatureSensor` — без изменений) плюс новый `FlowMeter` с собственным `GetDescription()`, для которого ветку в `switch` не добавили:

```csharp
// как в решении: список object и switch
foreach (var item in list)                                // List<object>
    Console.WriteLine(item switch
    {
        Pump p              => p.GetDescription(),
        GateValve g         => g.GetDescription(),
        TemperatureSensor t => t.GetDescription(),
        _                   => "Неизвестное устройство"
    });

// тот же обход: список общего базового типа и виртуальный вызов
foreach (var device in list)                              // List<Device>
    Console.WriteLine(device.GetDescription());
```

```
--- List<object> + switch ---
Устройство Насос 1, давление 0 Бар
Устройство Задвижка 1, задвижка Открыта
Устройство Датчик температуры 1, температура 50 С
Неизвестное устройство                                   ← ветку забыли — тихо
--- List<Device> + виртуальный вызов ---
Устройство Насос 1, давление 0 Бар
Устройство Задвижка 1, задвижка Открыта
Устройство Датчик температуры 1, температура 50 С
Устройство Расходомер 1, расход 12,5 л/мин
```

Все три ветки `switch` делали одно и то же — выбор версии по фактическому типу, который виртуальный метод уже делает сам. `switch` понадобился только потому, что в `List<object>` у элементов нет `GetDescription`; общий тип `Device` при этом был. Это грабля 7 из 1.17: обобщённый параметр, который всегда подставляется одним типом.

**Цена двух устройств при изменениях требования:**

| Изменение | виртуальный метод + список базового типа | функции со `switch` по типу |
|---|---|---|
| новый вид устройства | один новый класс | класс + ветка **в каждой** функции; забыл ветку — тихая ошибка |
| новая операция над всеми | метод в базовом классе + в каждом наследнике | одна новая функция |

**Виртуальный метод делает дешёвым новый вид, `switch` — новую операцию.** Выбор — по тому, что меняется чаще. В задаче: «раз в месяц ставят новый вид прибора» → виртуальный метод. Решение, в котором есть и виртуальный метод, и `switch` поверх него, платит обе цены сразу.

Ещё два приёма, всплывших на разборе:

- **Шаблонный метод.** Если наследники дописывают своё *после* `base.GetDescription()`, общий *конец* строки базовый класс добавить не может. Переворот: базовый класс собирает всю строку и спрашивает у наследника только изменяемую часть. Общий формат меняется в одном месте.

  ```csharp
  public class Device
  {
      public string Name { get; }
      public Device(string name) => Name = name;

      // Шаблон строки. НЕ virtual: формат принадлежит базовому классу.
      public string GetDescription()
          => $"[{Name}] {Details()} — {(HasConnection ? "связь есть" : "нет связи")}";

      protected virtual string Details() => "";          // «вопрос к наследнику»
      protected virtual bool HasConnection => true;       // по умолчанию связь есть
  }

  public class Pump(string name) : Device(name)
  {
      private double _pressure;
      private bool _lostConnection;                       // состояние — bool, а не текст для экрана

      public double Pressure
      {
          get => _pressure;
          set
          {
              if (value < 0) { _lostConnection = true; return; }   // отвергли, прежнее не трогаем
              _pressure = value;
              _lostConnection = false;
          }
      }

      protected override string Details() => $"давление {Pressure} бар";
      protected override bool HasConnection => !_lostConnection;
  }

  public class GateValve(string name) : Device(name)
  {
      public bool IsOpen { get; set; }
      protected override string Details() => IsOpen ? "открыта" : "закрыта";
  }

  public class TemperatureSensor(string name) : Device(name)
  {
      public int Temperature { get; set; }
      protected override string Details() => $"температура {Temperature} °C";
  }
  ```

  **[проверено]**: насос `Pressure = 4`, задвижка открыта, датчик 50; затем насосу пришло `-1`, затем `5`:

  ```
  --- обход 1 ---
  [Насос 1] давление 4 бар — связь есть
  [Задвижка 1] открыта — связь есть
  [Датчик 1] температура 50 °C — связь есть
  --- обход 2: пришло -1 ---
  [Насос 1] давление 4 бар — нет связи
  [Задвижка 1] открыта — связь есть
  [Датчик 1] температура 50 °C — связь есть
  --- обход 3: пришло 5 ---
  [Насос 1] давление 5 бар — связь есть
  ```

  Направление вызова перевёрнуто по сравнению с `base.GetDescription() + "…"`: не наследник вызывает базовый, а **базовый вызывает наследника**. `GetDescription()` обычный и выполняется сам; внутри он вызывает виртуальный `Details()`, и отвечает версия фактического объекта — полиморфизм работает внутри базового класса. `Details()` закрыт как `protected`: снаружи он никому не нужен (1.8). Забыть переопределить его наследник пока может молча — получит пустую середину строки; заставить каждого ответить позволяет `abstract` (2.2).
- **Правило о наборе держит владелец набора.** Уникальность имён устройство проверить не может — оно не знает о других. Её держит пультовая, но только если её список закрыт (`private`) и добавить устройство можно лишь через один метод, который правило проверяет. Открытый `List<T> { get; set; }` делает такое правило невыполнимым — инкапсуляция в чистом виде.

## 5б. Где встретится в реальном коде

- **`public override string ToString()`** — самый частый полиморфизм в обычном коде. Отладчик и `Console.WriteLine` показывают объект через него.
- **`protected override void OnStartup(...)` / `OnClosing` / `OnRender`** в WPF — точки расширения фреймворка. Узнаются по `override` и вызову `base.`, который нельзя забывать: без `base.OnStartup(e)` часть работы базового класса не выполнится.
- **Предупреждение CS0108 в старом коде** — почти всегда забытый `override`, а не намеренное сокрытие. Баг проявляется только при вызове через переменную базового типа.
- **Анализатор CA2214** «не вызывайте переопределяемые методы в конструкторах» — грабля 1. Если он срабатывает, вызов из конструктора стоит убрать, а не заглушить.
- **`switch` по типам (`case Pump p: ... case Valve v: ...`), повторённый в нескольких местах** — признак, что выбор по типу размножился. Иногда это осознанное решение, иногда — пропущенный виртуальный метод.
- **Базовые классы вроде `ViewModelBase`, `EntityBase`** — общий код для целого слоя приложения. Смотреть надо на то, является ли наследник тем, чем назван базовый класс, или наследование взято только ради пары методов.
