# 2.2 Абстрактный класс против интерфейса

Тема Блока 2, формат тот же, что в 2.1: предсказаний нет, задача — **типа 2**. Перед ней — 2–3 вопроса на понимание (шаг 2 цикла).

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

## 1. Зачем / какую проблему решает

В 2.1 полиморфизм держался на **базовом классе**: `Device` с виртуальным методом, наследники его переопределяют, пультовая обходит `List<Device>` и не знает конкретных типов. Остались два вопроса, на которые 2.1 не отвечала:

1. **Что, если у базового класса нет разумной собственной реализации?** Каким должно быть показание «устройства вообще»? Виртуальный метод с заглушкой `return "";` — обещание, которое никто не обязан выполнять: забыл переопределить — молча получил пустую строку.
2. **Что, если общее у типов — не происхождение, а умение?** «Умеет поднять тревогу» есть и у датчика температуры, и у насоса, и у двери щита. Общего предка у них нет и быть не должно. А базовый класс у C#-класса может быть **только один**.

Первый вопрос решает **абстрактный класс**: базовый класс, у которого часть членов объявлена без тела, и наследник **обязан** их дать — иначе не соберётся. Второй — **интерфейс**: набор членов, который может пообещать выполнить любой тип, независимо от того, от кого он унаследован.

Коротко: абстрактный класс говорит «**является** устройством и потому умеет то-то», интерфейс говорит «**умеет** то-то, а кем является — неважно».

> [док] [abstract (C# reference)](https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/abstract) · [interface (C# reference)](https://learn.microsoft.com/dotnet/csharp/language-reference/keywords/interface)

## 2. Как устроено

Всё, что ниже помечено **[проверено]**, получено на одной программе (.NET 10, Release). Она показана по частям, но целиком: каждый тип, который встречается в выводе, объявлен рядом с выводом. Ошибки компиляции получены сборкой той же программы с одной вставкой — вставка указана при каждой ошибке.

### Опыт 1: абстрактный класс — базовый класс с обязательствами

```csharp
public abstract class Device
{
    public string Name { get; }

    protected Device(string name)
    {
        Name = name;
        Console.WriteLine($"  конструктор Device: {name}");
    }

    public abstract string Reading();                     // тела нет: даёт наследник
    public string LogLine() => $"{Name}: {Reading()}";    // общий код, один на всех
}

public class Pump : Device
{
    public double Pressure { get; set; }
    public Pump(string name, double pressure) : base(name) => Pressure = pressure;
    public override string Reading() => $"{Pressure} бар";
}

Device d = new Pump("Н-1", 4.5);
Console.WriteLine(d.LogLine());
```

**[проверено]** вывод:

```
  конструктор Device: Н-1
Н-1: 4,5 бар
```

Что здесь видно:

- У абстрактного класса **есть всё, что есть у обычного**: состояние (`Name`), конструктор (он выполнился — первая строка вывода), готовые методы (`LogLine`). Наследование работает ровно как в 2.1, включая `: base(name)`.
- `abstract string Reading()` — **виртуальный метод без тела**. `LogLine` вызывает его, не зная, что там будет; ответ дал `Pump`. Это шаблонный метод из итога 2.1, только теперь «дыру» в шаблоне заполнить **обязательно**.

Чем абстрактный класс отличается от обычного — только запретами, и оба проверяет компилятор **[проверено]**:

| Вставка | Результат |
|---|---|
| `var x = new Device("x");` | `CS0144`: Не удается создать экземпляр абстрактного типа или интерфейса "Device" |
| `public class Valve : Device { public Valve() : base("З-1") { } }` — без `Reading()` | `CS0534`: "Valve" не реализует наследуемый абстрактный член "Device.Reading()" |

Первый запрет: «устройства вообще» не бывает, бывает конкретный насос. Второй — то самое обязательство: виртуальный метод с заглушкой забыть переопределить можно, абстрактный — нельзя.

### Опыт 2: интерфейс — одна роль, которую может взять любой

```csharp
public interface IReadable
{
    string Reading();
    string Line() => $"[{Reading()}]";                    // метод по умолчанию — опыт 3
}

public interface IAlarm
{
    bool IsAlarm { get; }
}

public class TempSensor : IReadable, IAlarm
{
    public string Name { get; }
    public double Celsius { get; }
    public TempSensor(string name, double celsius) { Name = name; Celsius = celsius; }
    public string Reading() => $"{Name}: {Celsius} °C";
    public bool IsAlarm => Celsius > 90;
}

var t = new TempSensor("Т-3", 95);
IReadable r = t;
IAlarm a = t;
Console.WriteLine($"{r.Reading()}, тревога: {a.IsAlarm}");
Console.WriteLine(ReferenceEquals(r, a));
```

**[проверено]** вывод:

```
Т-3: 95 °C, тревога: True
True
```

- Интерфейс — **только обещание**: какие члены есть, без состояния. Класс, который пишет `: IReadable`, обязан дать все члены без тела, иначе не соберётся (`CS0535`, опыт 5).
- Ролей у одного класса может быть **сколько угодно**: `TempSensor` одновременно и `IReadable`, и `IAlarm`.
- Последняя строка — `True`: `r` и `a` указывают на **один и тот же объект**. Интерфейсная переменная — это не копия и не обёртка, а та же ссылка (1.1), через которую видны только члены этой роли. Как у `Device d = new Pump(...)` в 2.1.

#### Зачем вообще `IReadable r = t`, если можно вызвать `t.Reading()`

Можно, и в опыте присваивания нужны только затем, чтобы показать одну ссылку под двумя ролями. Члены интерфейса — обычные `public`-члены класса, через `t` они вызываются напрямую. *(Добавлено по вопросу пользователя.)*

Интерфейсная переменная нужна **не там, где объект создают, а там, где его используют, не зная класса**. Тогда то же присваивание происходит неявно: при передаче в параметр или при добавлении в список. **[проверено]**:

```csharp
public class CabinetDoor : IAlarm            // дверь щита: не датчик, общего предка с TempSensor нет
{
    public string Name { get; }
    public bool IsOpen { get; }
    public CabinetDoor(string name, bool isOpen) { Name = name; IsOpen = isOpen; }
    public bool IsAlarm => IsOpen;
}

var t = new TempSensor("Т-3", 95);
Console.WriteLine($"{t.Reading()}, тревога: {t.IsAlarm}");   // напрямую — можно

var alarms = new List<IAlarm> { t, new CabinetDoor("Щит-2", isOpen: true), new TempSensor("Т-4", 40) };
PrintAlarms(alarms);

static void PrintAlarms(List<IAlarm> items)    // знает только роль, о классах — ничего
{
    foreach (var item in items)
        Console.WriteLine($"{item.GetType().Name}: {item.IsAlarm}");
}
```

```
Т-3: 95 °C, тревога: True
TempSensor: True
CabinetDoor: True
TempSensor: False
```

`PrintAlarms` написан один раз и работает с датчиком и дверью, хотя у них нет общего базового класса. Добавится третий тип с тревогой — `PrintAlarms` менять не надо. Это полиморфизм из 2.1, только опора у него не базовый класс, а роль. (В этом прогоне `TempSensor` реализует только `IAlarm` — `IReadable` для примера не нужен.)

Единственный случай, где через переменную класса **не получится**, — метод по умолчанию из опыта 3.

Запреты интерфейса **[проверено]**:

| Вставка | Результат |
|---|---|
| `public interface IBad { int _x; }` | `CS0525`: Интерфейсы не могут содержать поля экземпляра |
| `public class Both : Pump, TempSensor { }` | `CS1721`: Класс "Both" не может иметь несколько базовых классов |

Второй запрет — к классам, а не к интерфейсам, но именно он делает интерфейсы необходимыми: базовый класс один, ролей — сколько угодно.

### Опыт 3: метод по умолчанию виден только через интерфейс

С C# 8 у члена интерфейса может быть тело — **метод по умолчанию**, как `Line()` выше. `TempSensor` свой `Line()` не писал.

```csharp
Console.WriteLine(r.Line());     // r — переменная типа IReadable
```

**[проверено]** вывод: `[Т-3: 95 °C]`

А через переменную класса — нет **[проверено]**:

| Вставка | Результат |
|---|---|
| `Console.WriteLine(t.Line());` — `t` типа `TempSensor` | `CS1061`: "TempSensor" не содержит определения "Line", и не удалось найти доступный метод расширения "Line"… |

Метод по умолчанию **не становится членом класса**. Он принадлежит интерфейсу, и компилятор находит его, только когда переменная объявлена интерфейсом. Это тот же принцип, что в 1.16: какой метод доступен, решает **объявленный тип переменной**. Обрати внимание на текст ошибки — компилятор, не найдя `Line` у класса, честно поискал ещё и метод расширения (шаг 2 из 1.16).

> [док] [Default interface methods](https://learn.microsoft.com/dotnet/csharp/advanced-topics/interface-implementation/default-interface-methods-versions)

### Опыт 4: структура за интерфейсом — упаковка

Интерфейс могут реализовать и структуры. Но интерфейсная переменная — ссылка, а у структуры ссылки нет.

```csharp
public interface ICounter
{
    int Count { get; }
    void Tick();
}

public struct Counter : ICounter
{
    public int Count { get; private set; }
    public void Tick() => Count++;
}

var c = new Counter();
ICounter ic = c;
ic.Tick();
ic.Tick();
Console.WriteLine($"c.Count = {c.Count}, ic.Count = {ic.Count}");
```

**[проверено]** вывод: `c.Count = 0, ic.Count = 2`

`ICounter ic = c;` — это **упаковка** (1.4): в куче создаётся коробка с **копией** `c`, и `ic` указывает на неё. Оба `Tick()` увеличили счётчик в коробке, а `c` остался нулём. Ровно то, что в очереди повторения записано как «упаковка не переносит значение, а создаёт новый объект с копией».

Цена в памяти — на каждый вызов метода, принимающего интерфейс **[проверено]**, 1 000 000 вызовов:

```csharp
static int ReadI(ICounter x) => x.Count;                       // параметр — интерфейс
static int ReadT<T>(T x) where T : ICounter => x.Count;        // параметр — T с ограничением (1.18)
```

```
ReadI: 24000000 байт, ReadT: 0 байт
```

24 байта на вызов — та же коробка, что в замере 1.16. Обобщённый метод с ограничением `where T : ICounter` получает саму структуру и упаковки не делает: ограничение даёт доступ к членам интерфейса **без** превращения в ссылку.

### Опыт 5: что ломается, когда контракт растёт

Самое практичное различие — не в том, что можно написать сегодня, а в том, что случится, когда в контракт добавят член. Каждая строка — вставка одной строки в программу из опытов 1–2 **[проверено]**:

| Добавили | Результат |
|---|---|
| в `IReadable`: `string Unit { get; }` — без тела | `CS0535`: "TempSensor" не реализует член интерфейса "IReadable.Unit" |
| в `IReadable`: `string Unit => "?";` — с телом по умолчанию | собрано без ошибок |
| в `Device`: `public abstract string Unit();` | `CS0534`: "Pump" не реализует наследуемый абстрактный член "Device.Unit()" |
| в `Device`: `public virtual string Unit() => "?";` | собрано без ошибок |

Вывод симметричный: **ломает только член без тела**, в интерфейсе и в абстрактном классе одинаково. Ломает он **всех** реализаторов сразу — у нас это по одному классу, в проекте могут быть десятки, и часть из них — в чужом коде, который ты не можешь поправить.

## 3. Синтаксис

```csharp
public abstract class Device                 // abstract — нельзя создать напрямую
{
    protected Device(string name) { }        // конструктор есть; protected — вызывает только наследник
    public abstract string Reading();        // без тела, наследник обязан override
    public virtual string Unit() => "";      // с телом, наследник может override
    public string LogLine() => "...";        // обычный, наследник не трогает
}

public class Pump : Device                   // один базовый класс…
    , IAlarm, IComparable<Pump>              // …и сколько угодно интерфейсов, через запятую после него
{
    public Pump() : base("Н-1") { }
    public override string Reading() => "4,5 бар";   // override — для абстрактного члена
    public bool IsAlarm => false;                     // для члена интерфейса override НЕ пишется
    public int CompareTo(Pump? other) => 0;
}

public interface IAlarm                      // имя с I — соглашение, не правило языка
{
    bool IsAlarm { get; }                    // public по умолчанию, писать не нужно
}
```

**[проверено]** этот блок собирается как есть. `new Pump()` → `LogLine()` даёт `...`, `Unit()` — пустую строку из базового класса, `IsAlarm` — `False`. И две ошибки, которые он предупреждает:

| Вставка | Результат |
|---|---|
| `public class Pump : IAlarm, Device, IComparable<Pump>` — класс не первым | `CS1722`: Перед интерфейсом должен быть указан базовый класс "Device" |
| `public override bool IsAlarm => false;` — `override` у члена интерфейса | `CS0115`: "Pump.IsAlarm": не найден метод, пригодный для переопределения |

Порядок в списке после двоеточия: **сначала класс, потом интерфейсы**. Член интерфейса реализуется обычным `public`-членом без `override`: переопределять нечего, у интерфейса нет своей версии.

## 4. Грабли

**1. Метод по умолчанию не виден через класс.** Опыт 3. Добавили `Line()` с телом в интерфейс, пытаешься вызвать `sensor.Line()` — `CS1061`, «метода нет», хотя он вот он. Нужна переменная интерфейсного типа или приведение: `((IReadable)sensor).Line()`.

**2. Структура за интерфейсом — копия.** Опыт 4. Изменения через интерфейсную переменную уходят в коробку, оригинал их не видит. Плюс 24 байта на каждое такое приведение. Для структур, которые надо менять через интерфейс, — либо класс вместо структуры, либо обобщённый метод с ограничением.

**3. Добавить член без тела в опубликованный контракт — сломать всех.** Опыт 5. В своём проекте это десять ошибок компиляции, которые видно сразу. В библиотеке, которую подключают другие, — ошибки у людей, которых ты не знаешь, после обновления пакета.

**4. Абстрактный класс ради одного метода.** Если в абстрактном классе нет ни состояния, ни общего кода — только абстрактные члены, — это интерфейс, который зачем-то забрал у наследников единственное место базового класса.

**5. Интерфейс ради интерфейса.** `IPump` с единственной реализацией `Pump`, который никто не подменяет, — лишний файл и лишний шаг при навигации по коду. Интерфейс окупается, когда реализаций несколько или подмена реально нужна (тесты — 9.3, внедрение зависимостей — 2.8).

## 5. Когда что

| Ситуация | Что брать |
|---|---|
| у типов общие **данные** (имя, серийный номер) и общий код | абстрактный класс |
| общий код есть, но без «дыр», которые обязан заполнить наследник | обычный базовый класс (2.1) |
| общее — **умение**, и им обладают типы из разных иерархий | интерфейс |
| нужно несколько ролей у одного типа | интерфейсы: базовый класс один |
| роль должны уметь играть структуры | интерфейс (структура не наследует классы) — но помнить про упаковку |
| контракт будут реализовывать другие команды, а потом он будет расти | интерфейс с методами по умолчанию для новых членов — или абстрактный класс с виртуальными |

Частый ответ «и то и другое»: интерфейс задаёт роль, а абстрактный класс реализует её частично, чтобы наследникам не повторять общий код. Вызывающий код работает с интерфейсом и о базовом классе не знает.

## 5б. Где встретится в реальном коде

- **Рабочий проект, EF Core: оба приёма рядом.** `FasDbContext : DbContext` — наследование класса: контекст получает от `DbContext` всё его состояние и поведение (отслеживание изменений, подключение) и переопределяет `OnModelCreating`, `SaveChanges`. А каждая настройка таблицы — `internal sealed class CanUserConfiguration : IEntityTypeConfiguration<CanUser>` — реализация интерфейса с одним методом `Configure`. Их десятки, общего состояния у них нет, общее только умение «настроить таблицу» — интерфейс. `ApplyConfigurationsFromAssembly` находит их все, по-видимому, рефлексией (1.20) по этому интерфейсу. Механика EF — Блок 12.
- **`IComparable<T>`, `IEquatable<T>`, `IDisposable`** — роли из BCL. `where T : IComparable<T>` в 1.18 — это и было «любой тип, умеющий сравниваться», без общего предка.
- **`CS0535` после обновления пакета** — в интерфейс библиотеки добавили член без реализации по умолчанию. Если ошибка в чужом классе, который ты не трогал, — смотреть, что поменялось в версии пакета.
- **`CS1061` на методе, который «точно есть в интерфейсе»** — почти всегда метод по умолчанию, вызванный через переменную класса.
- **Пара `IDevice` + `DeviceBase`** — интерфейс задаёт роль, абстрактный класс с суффиксом `Base` даёт общий код. Если в проекте только `DeviceBase` без интерфейса, а наследники встречаются в разных иерархиях — кто-то уже упёрся в «один базовый класс».
