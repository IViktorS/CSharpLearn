# 9.8 CI: сборка на каждый push (вне очереди)

Тема взята вне очереди: на работе CI и CD есть (Bitbucket + Bamboo), пользователь ими пользуется, но в устройстве не разбирается. Учимся на GitHub Actions в этом же репозитории — `IViktorS/CSharpLearn`. Задачи — `9.8-CI-Tasks.md` в этой папке, сам workflow живёт в `.github/workflows/` в корне репозитория.

Пометки происхождения: **[проверено]** — запущено, результат приложен; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

**Особенность темы:** прогнать GitHub Actions на этой машине нельзя, их запускает только GitHub после push. Пометки `[проверено]` здесь — по настоящим прогонам пользователя 26–28 октября 2026 (вкладка Actions репозитория, прогоны #1–#12; публичные, их можно открыть). Где пометки нет — по-прежнему утверждение.

## 1. Зачем / какую проблему решает

«У меня собирается» — это утверждение про твою машину, а на ней много всего, чего нет в репозитории: установленные SDK, файлы, которые забыли закоммитить, результаты прошлых сборок. Вопрос, который действительно важен для команды, другой: **собирается ли то, что лежит в репозитории?**

**CI** (continuous integration, непрерывная интеграция) — автоматическая сборка, а позже и тесты, **на каждое изменение и на чистой машине**. На ней есть только то, что взято из репозитория. Ответ приходит через минуты после push, а не тогда, когда коллега попробует собрать твою ветку.

Два примера из этого репозитория:

- в разборе очереди №2 проект `Basics` целиком не собирался из-за одной тестовой строки. Запушь ты такое — коммит на GitHub стал бы красным;
- в корне лежит `Program.cs` (харнесс, попавший в коммит `0e410ec`), который не входит ни в один проект. CI его **не увидит**: проверяется только то, что строит решение.

**CD** (continuous delivery / deployment, непрерывная доставка / развёртывание) — следующий шаг. Результат сборки упаковывается и доставляется: как минимум — готовый **артефакт**, который можно скачать, как максимум — развёртывание на сервер или у заказчика. Коротко: CI отвечает «собирается ли и проходят ли тесты», CD — «вот готовое, и оно доставлено».

### На работе: Bitbucket + Bamboo

Bitbucket хранит код и pull request'ы, Bamboo собирает и разворачивает. Понятия переносятся почти один к одному. *Термины Bamboo — по описанию, без запуска: утверждение.*

| Понятие | GitHub Actions | Bamboo |
|---|---|---|
| что запускается целиком | workflow | план (plan) |
| крупные этапы | jobs | stages → jobs |
| шаги внутри | steps | tasks |
| машина, где выполняется | runner | agent |
| результат сборки | artifact | artifact |
| развёртывание | deployment job, environments | deployment project, environments |
| статус у коммита | check | build status в Bitbucket |

## 2. Как устроено

Цепочка от push до результата:

1. Ты пушишь коммит.
2. GitHub ищет в репозитории файлы `.github/workflows/*.yml`.
3. В каждом смотрит секцию `on`: реагирует ли этот workflow на такое событие (push, pull request) и такую ветку.
4. Если да — выделяет **чистую виртуальную машину** нужного вида (`runs-on`).
5. Выполняет шаги (`steps`) по очереди. Любой шаг, вернувший ошибку, останавливает job.
6. Результат — **статус у коммита** (✓ или ✗) и лог каждого шага на вкладке **Actions**.

[проверено] по прогонам:

- статус у коммита сначала «в процессе», потом ✓ или ✗; прогон этого репозитория занимает **около минуты** (53 с – 1 мин 18 с), дольше всего — `setup-dotnet`;
- упавший шаг (код выхода ≠ 0) останавливает job: следующие шаги **серые, пропущены**, а не красные (прогон #11 — `upload-artifact` пропущен после упавшего `dotnet build`);
- упавший job — красный весь прогон и ✗ у коммита;
- `run:` на `windows-latest` выполняется в **PowerShell**, на `ubuntu-latest` — в **bash**; корень репозитория на Windows-машине — `D:\a\CSharpLearn\CSharpLearn`, относительные пути в workflow считаются от него;
- ошибки и предупреждения компилятора GitHub выносит в блок **Annotations** на странице Summary прогона, с файлом и строкой. Каждая там дважды — `dotnet` печатает их по ходу сборки и в итоговой сводке.

Главное, что стоит держать в голове: **каждый прогон начинается с нуля.** На новой машине нет твоего кода, пока шаг `actions/checkout` его не скачает. Нужной версии .NET может не быть, пока `actions/setup-dotnet` её не поставит. Файлов от прошлого прогона нет вовсе.

**`uses` против `run`:**

| | Что это | Пример |
|---|---|---|
| `uses:` | готовое **действие** — чужой код из другого репозитория, с версией после `@` | `actions/checkout@v7` |
| `run:` | **команда оболочки** на машине прогона | `dotnet build ... -c Release` |

**Версии действий важны.** С 23 сентября 2026 года на машинах GitHub больше нет Node 20, а старые мажорные версии стандартных действий работали на нём. Актуальные на октябрь 2026, все на Node 24:

| Действие | Версия |
|---|---|
| `actions/checkout` | `@v7` |
| `actions/setup-dotnet` | `@v6` (умеет `dotnet-version: '10.0.x'`) |
| `actions/upload-artifact` | `@v7` |

> [док] [Node 20 is no longer available in GitHub Actions](https://github.blog/changelog/2026-09-23-node-20-is-no-longer-available-in-github-actions) · [actions/checkout](https://github.com/actions/checkout) · [actions/setup-dotnet](https://github.com/actions/setup-dotnet) · [actions/upload-artifact](https://github.com/actions/upload-artifact)

## 3. Синтаксис

Пример для **одного консольного проекта** — у задачи требования другие, это только образец записи:

```yaml
name: build                         # имя, которое видно на вкладке Actions

on:                                 # на какие события запускаться
  push:
    branches: [ master ]
  pull_request:
    branches: [ master ]

jobs:
  build:                            # имя job — любое
    runs-on: ubuntu-latest          # какую машину выделить
    steps:
      - uses: actions/checkout@v7               # скачать код репозитория
      - uses: actions/setup-dotnet@v6           # поставить .NET
        with:
          dotnet-version: '10.0.x'
      - run: dotnet build MyApp/MyApp.csproj -c Release
      - uses: actions/upload-artifact@v7        # выложить результат
        with:
          name: myapp
          path: MyApp/bin/Release/net10.0/
```

YAML строится **на отступах пробелами**: уровень вложенности — это отступ, а не скобки. Табуляция недопустима. Элемент списка начинается с `- `.

`branches` под `push` значит: «реагировать на push **в эти** ветки». Push в другую ветку этот workflow не запустит. [проверено]: push в ветку `ci-broken` прогона не дал ни одного.

`branches` под `pull_request` значит другое: ветка, **в которую** просят слить. Срабатывает, когда PR открыли или дописали — **до** слияния, а не при нём. [проверено]: PR `ci-broken → master` проверялся на каждый push в `ci-broken` (прогоны #9–#12), хотя так и не был слит. Само слияние — это push в `master`, его ловит триггер `push`.

Для PR берётся workflow **из проверяемой ветки**, а не из `master`. [проверено]: пока в `ci-broken` лежал workflow коллеги из задачи 4, PR проверялся им.

## 4. Грабли

**1. Тихие отказы — самые опасные.** Красный крестик по крайней мере видно. Хуже, когда CI выглядит зелёным, а на деле ничего не проверил. Таких отказов три класса:

- **не сработал запуск** — workflow не реагирует на твои события. Нет красного, но нет и зелёного: проверки просто не было;
- **запустился, но проверяет не всё** — часть решения в сборку не попала;
- **проверил, но ошибку проглотили** — шаг упал, а job настроен так, что падение не считается.

Признак любого из трёх — зелёный статус, которому нечем доверять. Проверяется одним способом: специально сломать то, что CI должен ловить, и убедиться, что он покраснел (задача 3).

**Все три класса — в одном workflow** (задача 4, ревью; разобрано 2026-10-28):

| Ошибка | Когда проявится | Почему | Как поймать |
|---|---|---|---|
| `branches: [ main ]`, а ветка — `master` | сразу и всегда | событие не наступает никогда — workflow **не запускается** | после push убедиться, что прогон **появился**: у коммита нет значка вовсе (не ✓ и не ✗), вкладка Actions пуста |
| `continue-on-error: true` у сборки | при любой ошибке компиляции | ключ делает два дела: **не останавливает** job и **не засчитывает** ему падение шага. Зелёный даёт второе | Summary прогона: статус Success, а в Annotations — errors. Противоречие видно без чтения лога. На ревью — спросить про каждый `continue-on-error`, зачем он |
| собирается `Basics/Basics.csproj`, а не решение | когда кто-то сломает WPF-проект — узнает тот, кто скачает `master` и соберёт у себя | второй проект просто не компилируется | сверить, *что* стоит после `dotnet build`, со списком проектов: в решении два, в строке один |
| артефакт из `CSharpLearn/bin/...` | **в каждом** прогоне | эту папку никто не собирал; по умолчанию `if-no-files-found: warn` | на ревью — есть ли `if-no-files-found: error`; на Summary — `Artifacts: –` |

Ошибки 3 и 4 разные (каждая остаётся, если исправить другую), но корень у них общий — WPF-проект не собирается.

**Итог ревью:** этот workflow не может покраснеть ни от какой ошибки в коде — сейчас он не запускается вовсе, а если починить ветку, зелёный при любой. «Всё зелёное» от коллеги не говорит ничего. Все четыре ошибки проявляются как **отсутствие сигнала**, поэтому их и пропускают.

[проверено] прогон #10 (этот workflow, только с `master` вместо `main`, в коде `int f = "ddd"`): статус **Success**; шаг `Build` в списке шагов — **✓ success**, падения там не видно вовсе; Annotations — **3 errors and 5 warnings**, среди них CS0029 и `No files were found`. Единственный след ошибки — счётчик аннотаций.

**2. `upload-artifact` по умолчанию не падает, если файлов нет.** [док]: при пути, по которому ничего не найдено, действие «выводит предупреждение, но не завершается ошибкой» — значение `if-no-files-found: warn` по умолчанию. Строгий вариант — `if-no-files-found: error`.

[проверено] одно и то же сообщение `No files were found with the provided path: ... No artifacts will be uploaded.` в двух прогонах: в #10 (по умолчанию) — предупреждение, прогон зелёный; в #8 (`path: CSharpLearnd/...` с `if-no-files-found: error`) — ошибка, прогон красный.

**3. У проекта WPF свои требования к машине.** [проверено] на `ubuntu-latest` (задача 2): сборка решения упала за ~1,4 с с **NETSDK1100** — SDK по умолчанию отказывается восстанавливать проект под `net10.0-windows` не на Windows. Упала на этапе **restore**, поэтому `Basics` тоже не скомпилировался, хотя он консольный. Свойство `EnableWindowsTargeting` из текста ошибки пропустило бы restore и сборку, но запустить WPF на Linux всё равно нечем — `windows-latest` выбран правильно, а не в обход.

[проверено] артефакт `csharplearn-wpf` — **5 файлов**: `CSharpLearn.deps.json`, `.dll`, `.exe`, `.pdb`, `.runtimeconfig.json`. Самой платформы .NET в нём нет: `runtimeconfig.json` требует установленных `Microsoft.NETCore.App 10.0` и `Microsoft.WindowsDesktop.App 10.0`. На машине без них `.exe` не запустится — утверждение, не проверено.

**3б. Этап, на котором упало, решает, сколько упало.** [проверено] на двух логах:

| | Linux, задача 2 | Windows, задача 3 |
|---|---|---|
| ошибка | NETSDK1100 | CS0029 в `Basics` |
| этап | restore — один на всё решение, до компиляции | компиляция — отдельно по проектам |
| что с другим проектом | не дошло до компиляции | `CSharpLearn -> ...CSharpLearn.dll` — **собрался** |
| итог | `Build FAILED`, exit code 1 | `Build FAILED`, exit code 1 |

Проекты не ссылаются друг на друга, поэтому ошибка компиляции одного не мешает другому. Если бы `CSharpLearn` ссылался на `Basics`, не собрался бы и он — утверждение. Для работы: упало «всё сразу» — сначала посмотреть этап. На restore — дело в окружении или пакетах, не в коде.

**4. Старые версии действий** — раздел 2. Пример из интернета с `@v3` или `@v4` сегодня может не запуститься.

**5. Каждый прогон с нуля** — нельзя рассчитывать, что на машине что-то осталось от прошлого раза.

**6. Предупреждения сборку не роняют.** [проверено] в прогоне #11 были CS0618 и CS8625 — прогон упал только из-за ошибки CS0029. Чтобы предупреждения роняли сборку, в `.csproj` ставят `<TreatWarningsAsErrors>true</TreatWarningsAsErrors>` или вызывают `dotnet build -warnaserror` — утверждение, не проверено. Стоит посмотреть, включено ли это в сборке на работе.

**7. Команду копировать без приглашения оболочки.** Строка `C:\CSharp\CSharpLearn> dotnet build ...` — это приглашение терминала плюс команда. Скопированная в `run:` целиком, она падает в PowerShell на машине прогона (было в задаче 1). В `run:` идёт только то, что после `>`.

## 5. Когда что

| Нужно | Что в workflow |
|---|---|
| узнать, собирается ли то, что в репозитории | шаг `dotnet build` всего решения |
| узнать, работает ли | шаг `dotnet test` — когда появятся тесты (Блок 9) |
| получить готовую сборку | `actions/upload-artifact` |
| развернуть куда-то | отдельный job развёртывания — этап 5 сквозного проекта |
| проверять pull request до слияния | `on: pull_request` |

## 5б. Где встретится в реальном коде

- **Красный крестик у коммита или pull request'а в Bitbucket** — статус, который поставил Bamboo. Клик по нему ведёт в лог сборки: искать шаг, на котором упало, и первую ошибку в его выводе — остальные часто её следствия.
- **«У меня собирается, а в Bamboo — нет»** — почти всегда разница между твоей машиной и чистой: незакоммиченный файл, локально установленный SDK или пакет, путь `C:\...`, которого на агенте нет.
- **Pull request нельзя смёржить, пока сборка не зелёная** — настройка репозитория (в Bitbucket — merge checks). Утверждение: как именно у вас настроено, видно в настройках репозитория.
- **Артефакт сборки в Bamboo** — то, что потом забирает проект развёртывания. Если развернулось «не то», смотрят, из какой сборки взят артефакт.
- **Workflow / план с `continue-on-error` или игнорируемыми тестами** — повод спросить на ревью, кто и почему разрешил падать молча.

## 6. Опирается на

Заполнено на шаге 6 (2026-10-28).

- **1.19 Атрибуты** — несущий молчаливый механизм. В логе задачи 3 предупреждение CS0618 от `[Obsolete("...")]` не уронило сборку: у атрибута параметр `error` по умолчанию `false`. С `[Obsolete("...", true)]` компилятор выдал бы ошибку CS0619, и прогон стал бы красным. Решение «упасть или нет» записано в самом атрибуте, читает его компилятор. Найдено с подсказки: первый ответ был «1.7, флаги по умолчанию» — идея «значение по умолчанию решает» верная, тема не та.
- **1.5 NRT** (код — из 1.17) — CS8625 тоже только предупреждение: аннотации NRT существуют для компилятора, в рантайме их нет.
- **Проверка типов компилятором** — CS0029 (`int f = "ddd"`): для пары `string → int` неявного преобразования нет. Отдельного номера у темы нет. Ответ «1.1» — следствие вопроса, а не промах: Claude ограничил поиск блоками 1–7, и пользователь взял ближайшую тему. Почему не 1.1: `object o = 5;` тоже переход от значимого к ссылочному, но компилируется (упаковка, 1.4).

## 7. Будет позже

- **`dotnet test` в CI** — когда появятся тесты (9.1 и дальше): CI начинает отвечать не только «собирается», но и «работает».
- **Кэширование пакетов NuGet, матрица версий, параллельные job'ы** — ускорение и расширение; не нужны, пока прогон занимает минуты.
- **CD целиком** — релизы по тегам, развёртывание, секреты, окружения: этап 5 сквозного проекта (Блок 13).
