# 9.8 CI: сборка на каждый push (вне очереди)

Тема взята вне очереди: на работе CI и CD есть (Bitbucket + Bamboo), пользователь ими пользуется, но в устройстве не разбирается. Учимся на GitHub Actions в этом же репозитории — `IViktorS/CSharpLearn`. Задачи — `9.8-CI-Tasks.md` в этой папке, сам workflow живёт в `.github/workflows/` в корне репозитория.

Пометки происхождения: **[проверено]** — запущено, результат приложен; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

**Особенность темы:** прогнать GitHub Actions на этой машине нельзя, их запускает только GitHub после push. Поэтому почти всё про поведение прогонов здесь пока **утверждения**. Пометки `[проверено]` появятся после твоих настоящих прогонов, с их результатами.

## 1. Зачем / какую проблему решает

«У меня собирается» — это утверждение про твою машину, а на ней много всего, чего нет в репозитории: установленные SDK, файлы, которые забыли закоммитить, результаты прошлых сборок. Вопрос, который действительно важен для команды, другой: **собирается ли то, что лежит в репозитории?**

**CI** (continuous integration, непрерывная интеграция) — автоматическая сборка, а позже и тесты, **на каждое изменение и на чистой машине**. На ней есть только то, что взято из репозитория. Ответ приходит через минуты после push, а не тогда, когда коллега попробует собрать твою ветку.

Два примера из этого репозитория:

- в разборе очереди №2 проект `Basics` целиком не собирался из-за одной тестовой строки. Запушь ты такое — коммит на GitHub стал бы красным;
- в корне лежит `Program.cs` (харнесс, попавший в коммит `0e410ec`), который не входит ни в один проект. CI его **не увидит**: проверяется только то, что строит решение.

**CD** (continuous delivery / deployment, непрерывная доставка / развёртывание) — следующий шаг. Результат сборки упаковывается и доставляется: как минимум — готовый **артефакт**, который можно скачать, как максимум — развёртывание на сервер или у заказчика. Коротко: CI отвечает «собирается ли и проходят ли тесты», CD — «вот готовое, и оно доставлено».

### На работе: Bitbucket + Bamboo

Bitbucket хранит код и pull request'ы, Bamboo собирает и разворачивает. Понятия переносятся почти один к одному. *Термины Bamboo — по описанию, без запуска: утверждение.*

| Понятие | GitHub Actions | Bamboo |
|---|---|---|
| что запускается целиком | workflow | план (plan) |
| крупные этапы | jobs | stages → jobs |
| шаги внутри | steps | tasks |
| машина, где выполняется | runner | agent |
| результат сборки | artifact | artifact |
| развёртывание | deployment job, environments | deployment project, environments |
| статус у коммита | check | build status в Bitbucket |

## 2. Как устроено

Цепочка от push до результата:

1. Ты пушишь коммит.
2. GitHub ищет в репозитории файлы `.github/workflows/*.yml`.
3. В каждом смотрит секцию `on`: реагирует ли этот workflow на такое событие (push, pull request) и такую ветку.
4. Если да — выделяет **чистую виртуальную машину** нужного вида (`runs-on`).
5. Выполняет шаги (`steps`) по очереди. Любой шаг, вернувший ошибку, останавливает job.
6. Результат — **статус у коммита** (✓ или ✗) и лог каждого шага на вкладке **Actions**.

Главное, что стоит держать в голове: **каждый прогон начинается с нуля.** На новой машине нет твоего кода, пока шаг `actions/checkout` его не скачает. Нужной версии .NET может не быть, пока `actions/setup-dotnet` её не поставит. Файлов от прошлого прогона нет вовсе.

**`uses` против `run`:**

| | Что это | Пример |
|---|---|---|
| `uses:` | готовое **действие** — чужой код из другого репозитория, с версией после `@` | `actions/checkout@v7` |
| `run:` | **команда оболочки** на машине прогона | `dotnet build ... -c Release` |

**Версии действий важны.** С 23 сентября 2026 года на машинах GitHub больше нет Node 20, а старые мажорные версии стандартных действий работали на нём. Актуальные на октябрь 2026, все на Node 24:

| Действие | Версия |
|---|---|
| `actions/checkout` | `@v7` |
| `actions/setup-dotnet` | `@v6` (умеет `dotnet-version: '10.0.x'`) |
| `actions/upload-artifact` | `@v7` |

> [док] [Node 20 is no longer available in GitHub Actions](https://github.blog/changelog/2026-09-23-node-20-is-no-longer-available-in-github-actions) · [actions/checkout](https://github.com/actions/checkout) · [actions/setup-dotnet](https://github.com/actions/setup-dotnet) · [actions/upload-artifact](https://github.com/actions/upload-artifact)

## 3. Синтаксис

Пример для **одного консольного проекта** — у задачи требования другие, это только образец записи:

```yaml
name: build                         # имя, которое видно на вкладке Actions

on:                                 # на какие события запускаться
  push:
    branches: [ master ]
  pull_request:
    branches: [ master ]

jobs:
  build:                            # имя job — любое
    runs-on: ubuntu-latest          # какую машину выделить
    steps:
      - uses: actions/checkout@v7               # скачать код репозитория
      - uses: actions/setup-dotnet@v6           # поставить .NET
        with:
          dotnet-version: '10.0.x'
      - run: dotnet build MyApp/MyApp.csproj -c Release
      - uses: actions/upload-artifact@v7        # выложить результат
        with:
          name: myapp
          path: MyApp/bin/Release/net10.0/
```

YAML строится **на отступах пробелами**: уровень вложенности — это отступ, а не скобки. Табуляция недопустима. Элемент списка начинается с `- `.

`branches` под `push` значит: «реагировать на push **в эти** ветки». Push в другую ветку этот workflow не запустит.

## 4. Грабли

**1. Тихие отказы — самые опасные.** Красный крестик по крайней мере видно. Хуже, когда CI выглядит зелёным, а на деле ничего не проверил. Таких отказов три класса:

- **не сработал запуск** — workflow не реагирует на твои события. Нет красного, но нет и зелёного: проверки просто не было;
- **запустился, но проверяет не всё** — часть решения в сборку не попала;
- **проверил, но ошибку проглотили** — шаг упал, а job настроен так, что падение не считается.

Признак любого из трёх — зелёный статус, которому нечем доверять. Проверяется одним способом: специально сломать то, что CI должен ловить, и убедиться, что он покраснел (задача 3).

**2. `upload-artifact` по умолчанию не падает, если файлов нет.** [док]: при пути, по которому ничего не найдено, действие «выводит предупреждение, но не завершается ошибкой» — значение `if-no-files-found: warn` по умолчанию. Строгий вариант — `if-no-files-found: error`.

**3. У проекта WPF свои требования к машине.** Какие именно и что будет, если их не выполнить, — задача 2.

**4. Старые версии действий** — раздел 2. Пример из интернета с `@v3` или `@v4` сегодня может не запуститься.

**5. Каждый прогон с нуля** — нельзя рассчитывать, что на машине что-то осталось от прошлого раза.

## 5. Когда что

| Нужно | Что в workflow |
|---|---|
| узнать, собирается ли то, что в репозитории | шаг `dotnet build` всего решения |
| узнать, работает ли | шаг `dotnet test` — когда появятся тесты (Блок 9) |
| получить готовую сборку | `actions/upload-artifact` |
| развернуть куда-то | отдельный job развёртывания — этап 5 сквозного проекта |
| проверять pull request до слияния | `on: pull_request` |

## 5б. Где встретится в реальном коде

- **Красный крестик у коммита или pull request'а в Bitbucket** — статус, который поставил Bamboo. Клик по нему ведёт в лог сборки: искать шаг, на котором упало, и первую ошибку в его выводе — остальные часто её следствия.
- **«У меня собирается, а в Bamboo — нет»** — почти всегда разница между твоей машиной и чистой: незакоммиченный файл, локально установленный SDK или пакет, путь `C:\...`, которого на агенте нет.
- **Pull request нельзя смёржить, пока сборка не зелёная** — настройка репозитория (в Bitbucket — merge checks). Утверждение: как именно у вас настроено, видно в настройках репозитория.
- **Артефакт сборки в Bamboo** — то, что потом забирает проект развёртывания. Если развернулось «не то», смотрят, из какой сборки взят артефакт.
- **Workflow / план с `continue-on-error` или игнорируемыми тестами** — повод спросить на ревью, кто и почему разрешил падать молча.

## 7. Будет позже

- **`dotnet test` в CI** — когда появятся тесты (9.1 и дальше): CI начинает отвечать не только «собирается», но и «работает».
