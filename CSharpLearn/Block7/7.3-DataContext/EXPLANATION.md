# 7.3 DataContext — наследование по дереву

Задачи — `DataContextTree.xaml` (+ `.xaml.cs` с кнопками). Запуск:

```bash
dotnet run --project CSharpLearn -- 7.3
```

Пометки происхождения: **[проверено]** — собрано и запущено в харнессе (консольный проект с `UseWPF`, дерево собирается в коде, значения читаются напрямую), вывод приложен; **[док]** — ссылка на документацию; без пометки — утверждение Claude.

> Мини-справка: **`{Binding Name}`** — «возьми свойство `Name` у источника и покажи здесь». Режимы, направления и прочее — тема 7.4. Здесь биндинг нужен только затем, чтобы было видно, какой источник он нашёл.

> Мини-справка: **`DataContext` — особое свойство WPF** (dependency property, тема 8.1). Отличие от обычного свойства из 1.6 в одном: его значение может быть **своим** или **пришедшим от родителя**, и WPF умеет сказать, какое из двух. Спрашивается это так: `DependencyPropertyHelper.GetValueSource(элемент, FrameworkElement.DataContextProperty)`. Ответ `Local` — значение задано у самого элемента, `Inherited` — пришло сверху.

## 1. Зачем / какую проблему решает

Биндингу нужен источник — объект, у которого он возьмёт свойство. Указывать источник в каждом биндинге — копипаста: на форме с двадцатью полями одно и то же двадцать раз.

`DataContext` — **источник по умолчанию**. Задаётся один раз наверху, и всё дерево ниже его видит. Биндинг без явного источника ищет его именно здесь.

Важно, что именно исчезает из биндинга. **Источник** — да; **путь к свойству** — нет:

| | Где задаётся |
|---|---|
| **источник** — объект, у которого берут свойство | один раз, в `DataContext` |
| **путь** — какое свойство у этого объекта | в каждом биндинге, всегда |

Вместо `{Binding Source={StaticResource vm}, Path=Name}` пишется `{Binding Name}`. Путь (`Name`, `Home.City`) остаётся — он и есть содержание биндинга. **[проверено]**:

```
DataContext есть, Binding("Name")       -> Иванов
DataContext есть, Binding("Home.City")  -> Псков
DataContext НЕТ,  Binding("Name")       -> <пусто>, без исключения
DataContext НЕТ,  Source=vm             -> Иванов
```

И выгода здесь не в экономии букв. Разметка, в которой не назван конкретный источник, **не привязана к конкретному объекту**: тот же XAML применяется к другому экземпляру простой подменой `DataContext`. На этом стоят и MVVM, и шаблоны данных (8.3) — шаблон элемента списка не знает, какой именно элемент рисует.

Это же — точка, на которой держится MVVM (7.9): окну один раз ставится `DataContext` = объект с данными, и вся разметка работает от него.

> [док] [Data binding overview — DataContext](https://learn.microsoft.com/dotnet/desktop/wpf/data/#data-context)

## 2. Как устроено

### Наследование значения по дереву

Поставил `DataContext` у корня — все потомки получают **то же значение**, пока кто-то ниже не поставил своё.

**[проверено]**, дерево `StackPanel → Border → TextBlock`, у корня `DataContext = Person("Анна")`:

```
StackPanel root ─────────── DataContext = Анна   ← Local (задан здесь)
├── Border border ───────── DataContext = Анна   ← Inherited
│   └── TextBlock inner ─── DataContext = Анна   ← Inherited
└── TextBlock sibling ───── DataContext = Анна   ← Inherited

inner.DataContext — тот же объект, что у root?  True
```

Две вещи из этого вывода:

- **Это один и тот же объект**, а не копии. Наследуется ссылка — прямое следствие 1.1: `Person` — класс, копируется адрес. Потомков у корня хоть сто — объект один.
- **Значение у потомка не лежит в нём самом**, оно «приходит» от родителя. WPF это различает (`Local` против `Inherited`), и дальше это различие окажется главным механизмом темы.

### Ближний перекрывает дальний

Поставил `DataContext` у элемента в середине — он и всё его поддерево видят новое значение, остальные — старое.

**[проверено]**, у `border` поставили `Person("Борис")`:

```
StackPanel root ─────────── Анна    ← Local
├── Border border ───────── Борис   ← Local      поставили ЗДЕСЬ
│   └── TextBlock inner ─── Борис   ← Inherited  от border, не от root
└── TextBlock sibling ───── Анна    ← Inherited  от root, замены не заметил
```

Граница проходит по поддереву: всё, что ниже `border`, переключилось на Бориса, всё, что в стороне, осталось на Анне.

Похоже на ресурсы из 7.2 — там тоже «вверх по дереву, ближний выигрывает». Отличие существенное: ресурс **ищется по ключу**, а `DataContext` — это **значение свойства**, которое течёт сверху вниз.

### Наследование живое

Заменили значение у корня — все, кто наследует, подхватывают **сразу**. Те, у кого своё, не замечают.

**[проверено]**, корню дали `Person("Вера")`, у `border` по-прежнему свой `Борис`:

```
StackPanel root ─────────── Вера    ← Local      заменили Анну на Веру
├── Border border ───────── Борис   ← Local      своё значение, замену не заметил
│   └── TextBlock inner ─── Борис   ← Inherited  от border
└── TextBlock sibling ───── Вера    ← Inherited  подхватил СРАЗУ
```

В терминах 7.2 это поведение `DynamicResource`, а не `StaticResource`: связь с источником держится постоянно.

### Вне дерева — ничего

**[проверено]**:

```
TextBlock, не добавленный в дерево:       DataContext = null
после root.Children.Add(этот TextBlock):   DataContext = <то, что у root>
```

Наследовать не от кого, пока нет родителя. Добавили — унаследовал мгновенно.

## 3. Синтаксис

**В коде** — обычное присваивание:

```csharp
Root.DataContext = new Person { Name = "Анна" };
```

**В XAML, объектом прямо в разметке** — через элементный синтаксис:

```xml
<Border>
    <Border.DataContext>
        <local:Person Name="Борис" />
    </Border.DataContext>
    ...
</Border>
```

**Через биндинг на вложенный объект** — самый частый в реальном коде вариант:

```xml
<StackPanel DataContext="{Binding Operator}">
    <TextBlock Text="{Binding Name}" />      <!-- это Operator.Name -->
    <TextBlock Text="{Binding Shift}" />     <!-- это Operator.Shift -->
</StackPanel>
```

Без этого пришлось бы писать `Operator.Name`, `Operator.Shift` в каждой строке.

**`{Binding}` без пути** — сам `DataContext` целиком. **[проверено]**: показывает его `ToString()`.

```
{Binding Name}  -> Вера
{Binding}       -> Person(Вера)
```

## 4. Грабли

**1. `= null` не возвращает наследование — оно его перекрывает.**

Самая неочевидная вещь темы. Кажется, что «обнулить» значит «убрать своё значение и снова смотреть на родителя». На деле `null` — это **тоже своё значение**, просто пустое.

**[проверено]**, у `border` был свой `Борис`, корень — `Вера`:

```
border.DataContext = null                         border.ClearValue(DataContextProperty)

root ─────────── Вера   ← Local                   root ─────────── Вера   ← Local
├── border ───── null   ← Local  (своё!)          ├── border ───── Вера   ← Inherited
│   └── inner ── null   ← Inherited от border     │   └── inner ── Вера   ← Inherited
└── sibling ──── Вера   ← Inherited               └── sibling ──── Вера   ← Inherited
```

После `= null` источник по-прежнему `Local`: элемент продолжает перекрывать родителя, только пустотой. Вернуть наследование можно только одним способом — **убрать** своё значение: `ClearValue(FrameworkElement.DataContextProperty)`.

Та же разница, что между «положить в коробку пустоту» и «убрать коробку».

**2. `DataContext` через биндинг на пустое свойство — та же грабля с другой стороны.**

Если `DataContext="{Binding Operator}"`, а `Operator` оказался `null`, блок **не откатывается** к `DataContext` родителя. Биндинг — это своё значение элемента, и его результат `null` перекрывает наследование ровно как в грабле 1.

Разметка одна и та же в обоих случаях:

```xml
<Border DataContext="{Binding Operator}">      <!-- block -->
    <TextBlock Text="{Binding Name}" />
</Border>
```

У родителя лежит `Machine`, и у него **тоже есть свойство `Name`** — «Станок-7». Отсюда и правдоподобная, но неверная версия: «оператора нет, значит `{Binding Name}` возьмёт имя станка».

**[проверено]**, два прогона:

```
  Operator = Person("Иванов")                    Operator = null

  Border parent ─ Machine        ← Local         Border parent ─ Machine        ← Local
  │               Name = Станок-7                │               Name = Станок-7
  │                                              │
  └─ Border block ─ Person(Иванов) ← Local       └─ Border block ─ null         ← Local
     │              задан биндингом                 │              биндинг вернул null,
     │              {Binding Operator}              │              но значение всё равно СВОЁ
     │                                              │
     └─ TextBlock ─ {Binding Name} = [Иванов]       └─ TextBlock ─ {Binding Name} = []
```

Справа `TextBlock` показывает **пустоту, а не «Станок-7»** — хотя `Machine` с этим именем никуда не делся и лежит прямо над ним.

Причина в правой колонке `← Local`: у `block` значение **своё**, поставленное биндингом. То, что биндинг вернул `null`, ничего не меняет — это по-прежнему собственное значение элемента, и оно перекрывает родителя. Поиск вверх по дереву **не возобновляется**: наследование включается только там, где своего значения нет вовсе (см. граблю 1 про `ClearValue`).

**3. Опечатка в пути — тихая пустота.**

**[проверено]**: `{Binding Nmae}` → текст пустой, исключения нет, программа работает дальше. Сравни с 7.2, где опечатка в `StaticResource` роняла окно при загрузке. Биндинг не падает никогда — он молча показывает ничего.

**4. Замена `DataContext` обновляет экран, правка объекта — нет.**

**[проверено]**:

```
после ЗАМЕНЫ DataContext у root:          inner.Text = [Глеб]
после ПРАВКИ Name у того же объекта:      inner.Text = [Глеб]    (сам объект: Person(Дина))
```

Объект уже «Дина», а на экране «Глеб». Замену видно, потому что `DataContext` — свойство элемента, и элемент сообщает об его изменении. Правку не видно, потому что наш `Person` сообщать об изменениях своих свойств **не умеет**. Как научить — тема 7.6, здесь это чёрный ящик.

Обрати внимание на зеркальность с 7.2. Там **правка** кисти обновила экран даже через `StaticResource`, потому что кисть сообщать умеет. Здесь правка не обновила ничего. Отличие не в `DataContext` и не в ресурсах, а в том, **умеет ли сам объект сообщать о своих изменениях**.

**5. Элемент вне дерева `DataContext` не получает** — см. раздел 2. Практически это всплывает у вещей, которые визуально рядом, но в дерево не входят (см. 5б).

## 5. Когда что

| Нужно | Как |
|---|---|
| один источник на всё окно | `DataContext` у корня, один раз |
| блок работает с вложенным объектом | `DataContext="{Binding Вложенный}"` у блока |
| поддереву нужен совсем другой источник | свой `DataContext` у корня поддерева |
| вернуть поддерево к источнику родителя | `ClearValue(FrameworkElement.DataContextProperty)`, **не** `= null` |
| показать «ничего» вместо данных | `= null` — и понимать, что наследование этим тоже отрезано |
| отдельный биндинг должен смотреть не в `DataContext`, а в другой элемент | `ElementName` / `RelativeSource` — тема 7.4 |

## 5б. Где встретится в реальном коде

- **Поле на форме пустое, исключения нет.** Первый подозреваемый — `DataContext` не тот, что ты думаешь (или опечатка в пути, грабля 3). Проверяется за секунду: временно поставь рядом `<TextBlock Text="{Binding}"/>` — он покажет, какой объект на самом деле является источником в этом месте.
- **Строки `System.Windows.Data Error: 40 : BindingExpression path error` в окне Output** при отладке. Это та самая тихая пустота из грабли 3 — WPF не бросает исключение, а пишет туда. Первое место, куда смотреть, когда «биндинг не работает».
- **`DataContext="{Binding SelectedItem}"` у панели с подробностями.** Пока ничего не выбрано, `SelectedItem` равен `null`, и панель пустая целиком — это грабля 2, а не ошибка. Иногда её прячут отдельной видимостью, иногда показывают заглушку.
- **Биндинг в столбце `DataGrid` не работает, хотя у таблицы `DataContext` правильный.** Столбец `DataGridColumn` — не элемент дерева, наследовать ему не от кого (грабля 5). Типичное решение, которое встретится в чужом коде, — прокси-объект в ресурсах или `x:Reference`.
- **`this.DataContext = this;` в конструкторе окна.** Встречается в коде без MVVM: окно само себе источник. Работает, но привязывает разметку к код-подложке. На ревью это обычно повод спросить, почему не отдельный объект с данными (7.9).
- **«Экран не обновляется после изменения данных»** — прежде чем подозревать `DataContext`, отличи замену от правки (грабля 4). Если меняют свойство у существующего объекта, а объект не умеет сообщать, `DataContext` ни при чём.

## 6. Опирается на

Назвал пользователь (что использовал):

- **1.5 `null`** — `Frame2.DataContext = null` в задаче 2 и `Operator = null` в задаче 3. В обоих случаях `null` оказывается **собственным значением элемента**, а не отсутствием значения, — и в этом вся грабля темы.
- **1.6 Свойства** — в трёх проявлениях: свойства у классов `Person`/`Machine`; **свойство, у которого тип — другой класс** (`Machine.Operator` типа `Person`), на чём и работают вложенные пути в биндингах; атрибут в XAML как присваивание свойства.

Назвал пользователь (что работает молча) — **верно**:

- **1.1 value vs reference** — несущая связь. Присваивание ссылки на новый объект против правки свойства у прежнего. Без ссылочной семантики кнопки «Заменить у корня» и «Переименовать» вообще не различались бы, а на их различии построена вся задача 2.

Дополнено при проверке:

- **1.7 `enum`** — `Orientation="Horizontal"` это член перечисления, а не строка; и `Local` / `Inherited`, вокруг которых крутится тема, — значения `BaseValueSource`, тоже `enum`. Третья тема WPF подряд, где перечисления работают и остаются неназванными.
- **1.9 `readonly` vs `const`** — та же ось «ссылка против содержимого», что и в 7.2: заменить объект и изменить объект дают разный результат. Здесь она объясняет разницу между кнопками 1 и 4.
- **1.14 Pattern matching** — в код-подложке, в методе `Rename`: `if (Root2.DataContext is Person p)`. Тип-паттерн с объявлением переменной, ровно из 1.14.

### Граница темы: где «правка объекта» перестаёт работать

В 7.2 замер показал, что правка кисти (`brush.Color = ...`) **сразу** отражается на экране, хотя объект не заменяли. Здесь правка `Person.Name` **не отражается никак** — экран показывает прежнее значение.

Разница не в `DataContext`, а в самом объекте: кисть — объект WPF со встроенным уведомлением об изменении, `Person` — обычный класс без него. Механизм уведомления (`INotifyPropertyChanged`) — тема 7.6.

Вывод, который стоит удержать: правило «правку объекта видно на экране», верное для встроенных типов WPF, **не переносится** на собственные классы.
