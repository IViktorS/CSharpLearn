# 7.2 StaticResource vs DynamicResource

Задачи: `Resources.xaml` в этой же папке. Запуск:

```
dotnet run --project CSharpLearn -- 7.2
```

Пометки происхождения: **[проверено]** — собрано и запущено, вывод приложен; без пометки — утверждение Claude, которое можно и нужно оспаривать.

## 1. Зачем / какую проблему решает

Один и тот же цвет, отступ, размер шрифта используется в двух десятках мест разметки. Написанный в каждом месте руками, он превращает смену фирменного цвета в двадцать правок и одну забытую.

Ресурс — это **именованное значение в словаре**, на которое ссылаются по ключу:

```xml
<Window.Resources>
    <SolidColorBrush x:Key="AccentBrush" Color="#0078D4" />
    <sys:Double x:Key="TitleSize">20</sys:Double>
</Window.Resources>

<TextBlock Foreground="{StaticResource AccentBrush}"
           FontSize="{StaticResource TitleSize}" />
```

Ресурсом может быть что угодно: кисть, число, строка, стиль, шаблон, произвольный объект.

## 2. Как устроено: словарь и поиск вверх по дереву

У каждого `FrameworkElement` есть свойство `Resources` — это `ResourceDictionary`, обычный словарь «ключ → объект». Такой словарь есть у любого элемента, у `Window` и у `Application`.

Когда разметка встречает ссылку на ресурс, поиск идёт **снизу вверх по дереву элементов**:

```
элемент → его родитель → ... → Window → Application → системные словари (тема ОС)
```

Первое совпадение выигрывает. Отсюда важное следствие: ресурс, объявленный ближе к месту использования, **перекрывает** одноимённый ресурс выше. Это способ локально переопределить значение, не трогая общее.

Ключ задаётся через `x:Key`. Ресурс без ключа в словаре — ошибка (единственное исключение — стили с `TargetType`, у которых ключ подразумевается; это тема 8.3).

## 3. Две ссылки — и в чём именно разница

**`StaticResource` — поиск выполняется один раз, при загрузке разметки.** Найденный объект подставляется в свойство, и связь на этом заканчивается. Словарь больше никто не переспрашивает.

**`DynamicResource` — ставится отложенная ссылка.** Значение тоже находится при загрузке, но связь сохраняется: если ресурс в словаре **заменят**, свойство обновится само.

**[проверено]**, замер на `Border` с кистью в его собственных ресурсах:

| Что сделали | `StaticResource` | `DynamicResource` |
|---|---|---|
| исходное значение | красный | красный |
| **заменили** объект в словаре | остался красный | стал зелёным |
| ключа в словаре нет | `ResourceReferenceKeyNotFoundException` | `null`, без исключения |

Три практических различия, кроме обновления:

- **Порядок объявления.** `StaticResource` ищет ресурс в момент разбора, поэтому ресурс должен быть объявлен **выше по файлу**, чем место использования. `DynamicResource` этого не требует — он ищет позже.
- **Цена.** `StaticResource` — один поиск и всё. `DynamicResource` хранит связь и переспрашивает словарь; применять его ко всему подряд не нужно.
- **Где применим.** `DynamicResource` можно присвоить только свойству зависимостей — обычному свойству CLR нельзя.

> Мини-справка: *свойство зависимостей* — особый вид свойства WPF, значение которого хранит не поле объекта, а внешняя система; благодаря этому оно умеет получать значение из нескольких источников и уведомлять об изменении. Подробно — тема 8.1. Здесь достаточно знать, что почти все свойства элементов управления (`Background`, `FontSize`, `Visibility`) именно такие.

## 4. Грабли

**1. «Заменить ресурс» и «изменить ресурс» — не одно и то же, и это главная ловушка темы.**

`StaticResource` не реагирует на **замену объекта** в словаре. Но он держит **ссылку на тот же самый объект**, что лежит в словаре, — и если этот объект **изменить**, изменение увидят все, кто на него ссылается, включая `StaticResource`.

**[проверено]**:

```
static, до правки  : #FFFF0000
brush.Color = Colors.Green        ← правим САМ объект, а не словарь
static, ПОСЛЕ правки: #FF008000   ← изменилось!
это тот же объект? True
```

Это ровно различие из темы 1.9: `readonly` защищает ссылку, а не содержимое. Здесь то же самое — «статичность» относится к ссылке, а не к состоянию объекта.

**2. Ресурс — один объект на всех.** Из предыдущего пункта следует: изменив кисть из ресурсов в одном месте, ты изменишь её везде. Это не побочный эффект, а устройство: словарь хранит один экземпляр, а не копию на каждого потребителя.

**3. `StaticResource` вперёд по файлу не работает.** Ссылка на ресурс, объявленный ниже, даёт ошибку при загрузке. Частый случай — ресурсы окна, написанные после разметки.

**4. Отсутствующий ключ ведёт себя по-разному.** `StaticResource` бросает исключение, `DynamicResource` **молчит** и оставляет свойство пустым. Опечатка в ключе `DynamicResource` не проявится никак — просто ничего не покрасится.

**5. Ресурсы окна не видны другому окну.** Поиск идёт вверх по дереву, а у второго окна своё дерево. Общее — только `Application.Resources`.

**6. Замороженную кисть изменить нельзя — но WPF не замораживает ресурсы сам.**

Заморозка (`Freezable.Freeze()`) делает объект неизменяемым ради производительности; попытка правки даёт `InvalidOperationException` **[проверено]**. Важно, что происходит она **только явно**:

| Откуда взялась кисть | `IsFrozen` |
|---|---|
| `new SolidColorBrush(...)` в коде | **False** |
| объявлена в XAML обычным образом | **False** |
| XAML + `po:Freeze="True"` (компилированный) | **True** |
| `Brushes.Red` | **True** |
| `SystemColors.WindowBrush` | **True** |

**[проверено]** — все пять строк замерены.

Как понять **без запуска**: `Brushes.X` и `SystemColors.X` заморожены всегда; `po:Freeze="True"` виден в разметке глазом; всё прочее не заморожено, пока кто-то не вызвал `.Freeze()`. Во время выполнения — свойство `IsFrozen`, в том числе в окне Watch. Защита в коде пишется как `if (!brush.IsFrozen)`.

> Угол, на который можно наткнуться: в «свободном» XAML, разбираемом через `XamlReader` во время выполнения, атрибут `mc:Ignorable="po"` заставляет парсер **пропустить** директиву `po:Freeze`. В компилированном XAML она работает, хотя `mc:Ignorable` стоит там же. **[проверено]** на обоих путях.

## 5. Когда что

| Ситуация | Что писать |
|---|---|
| Значение задано один раз и не меняется | `StaticResource` |
| Смена темы оформления во время работы | `DynamicResource` |
| Ресурс объявлен ниже по файлу | `DynamicResource` (или переставить объявление) |
| Ресурс приходит из системной темы ОС | `DynamicResource` |
| Массовое применение к сотням элементов | `StaticResource`, если нет нужды в обновлении |

Правило по умолчанию: **`StaticResource`**, а `DynamicResource` — там, где обновление действительно нужно. Обратный порядок («поставлю везде динамический на всякий случай») оплачивается лишней работой на каждом элементе и маскирует опечатки в ключах.

## 5б. Где встретится в реальном коде

Раздел без пометки `[проверено]` — это мой опыт, а не измерение. Оспаривай.

- **`App.xaml` с `MergedDictionaries`.** В любом WPF-проекте крупнее учебного ресурсы лежат не в окне, а в отдельных файлах (`Colors.xaml`, `Styles.xaml`), подключённых в `Application.Resources`. Первое, куда стоит заглянуть в незнакомом проекте, чтобы понять его оформление.
- **Переключение светлой и тёмной темы.** Практически единственный массовый сценарий, где `DynamicResource` обязателен: тема меняется подменой словаря, и все ссылки должны переехать сами.
- **Симптом «поменяли цвет, а половина элементов осталась старой».** Это `StaticResource` там, где нужен был динамический. Выглядит как «глючит через раз», хотя ведёт себя строго детерминированно.
- **Симптом «ничего не покрасилось, и ошибки нет».** Опечатка в ключе `DynamicResource`. Самый неприятный вид ошибки — молчаливый; в логах пусто, в окне вывода пусто.
- **На ревью:** `DynamicResource`, расставленный «на всякий случай» по всей разметке. Стоит денег на каждом элементе и маскирует опечатки в ключах (см. предыдущий пункт).
- **Ресурсы как способ шарить не только кисти.** В реальных проектах через словарь раздают конвертеры (8.2), шаблоны (8.3) и даже объекты-настройки. Механизм тот же, тип значения любой.

## 6. Опирается на

Назвал пользователь (что использовал):

- **1.1 value vs reference** — кисть это ссылочный тип, и вся разница между «заменить ресурс» и «изменить кисть» держится именно на этом. Без ссылочной семантики ловушки бы не существовало.
- **1.9 `readonly` vs `const`** — буквальная, не аналогия: там `readonly` защищает ссылку и не защищает содержимое, здесь «статичность» `StaticResource` относится к ссылке и не относится к состоянию объекта. Один механизм, два синтаксиса.
- **1.6 Свойства** — атрибут в разметке есть присваивание свойства.

Дополнено при проверке (что работает молча):

- **1.4 Boxing.** `ResourceDictionary` — словарь **`object` → `object`** (проверено рефлексией: `System.Object this[System.Object]`). Значит ресурс-число `<sys:Double x:Key="TitleSize">22</sys:Double>` лежит в словаре **упакованным**, и достать его можно только точным приведением: `(double)` работает, `(float)` даёт `InvalidCastException` **[проверено]**. Коробка создаётся один раз при укладке, а не на каждое чтение — два обращения подряд дают одну и ту же ссылку, поэтому цена разовая.

### Проверено дополнительно

**Ссылка вперёд не ловится сборкой.** XAML с `StaticResource` на ресурс, объявленный ниже, компилируется **без единой ошибки** и падает `XamlParseException` при загрузке. Причина: компилятор XAML переводит разметку в BAML, а поиск ресурса выполняется при загрузке. Практическое следствие — такая ошибка доедет до пользователя, если окно открывается редко.

**После замены связь разорвана окончательно.** Замер цепочки «замена, потом правка»:

```
старт         static=красный   dynamic=красный
после ЗАМЕНЫ  static=красный   dynamic=зелёный
после ПРАВКИ  static=красный   dynamic=синий     ← правим кисть, лежащую в словаре СЕЙЧАС
```

`StaticResource` держит **старый** объект, в словаре лежит новый — поэтому правка словарной кисти его уже не касается.

## 7. Будет позже

- **Стили без ключа** (`Style` с `TargetType`) — неявное применение ко всем элементам типа: тема 8.3.
- **`ResourceDictionary` в отдельном файле** и `MergedDictionaries` — как ресурсы раскладывают по файлам в реальных проектах.
- **Свойства зависимостей** (8.1) — почему `DynamicResource` работает только с ними.
- **`x:Shared="False"`** — как заставить словарь отдавать новый экземпляр каждому потребителю вместо общего.
